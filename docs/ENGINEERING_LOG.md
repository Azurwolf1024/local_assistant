### 1.3 要不要上 agent 执行循环（多轮工具）？——实测：不用

「模型 → 工具 → 把结果喂回去 → 模型再决定」这套循环（ReAct / agent harness）听起来更完备，
所以先用真实模型量了一遍：16 个样本（8 个普通多步 + 4 个「必须先看结果才能决定」+ 4 个
「压根不可能完成」），上限 8 轮。

| 看到的现象 | 实测数字 |
| --- | --- |
| 用了几轮工具 | **每条都只用 1 轮**——模型自己会把多个工具塞进同一轮（「日程+提醒+备忘」三个一起调） |
| 会不会转不出来 | 0 次用满上限、0 次重复调用 |
| 工具报错后会不会重试 | 不会（4 条不可能完成的任务都是 1 轮工具 → 直接道歉），所以也没机会进死循环 |
| 每多一轮的代价 | **+2~5s**（首轮 3.3~5.7s；每一轮都要重新预填一遍上下文） |
| 多轮之后的回答 | 模型会**改写**工具的说法：把「已取消今天晚上十点的提醒：练琴」换成「好的，已经帮您取消啦～下次可以说得更具体一点」，还夹带提议 |

结论：**默认保持单轮**（结构上就不存在死循环，比任何超时/计数都可靠）；
而且现在念的是工具产出的话，比让模型复述更准（复述会改数字，这是以前实测过的）。

> 单轮也有代价：模型只能根据**一句话**决定调哪些工具。真要它「先查再决定」
> （例：「找个空的下午排练，然后记上」），它现在会反问一句，而不是自己完成——
> 这也是一种可接受的答话。

如果哪天真要开多轮，三道保险一个都不能少（写在这里，免得到时候只加循环不加保险）：

1. **轮数硬上限**（2~3），到顶就把目前最好的话（工具 reply）念出去；
2. **重复调用检测**：同一轮同名同参再次出现 → 立刻停（小模型最常见的卡法）；
3. **连续失败即停**：工具返回 `ok=false` 两次就停，把失败原文念出来——
   小模型看到错误提示很容易开始反复重试。

另外记一条同一天的发现：这类探针很有用——它抳出了一个真 bug（见 5.3 节「没听懂的时间段
不会拿今天顶替」），而死循环那部分只花了 16 次调用就排除了。

### 语音自动打断里用过的东西（实验性，默认关）

打开后（`enabled = true`）它在**戴耳机**时最接近可用：基准会跟到底噪附近，
任何说话都能立刻打断；外放时确实不如耳机灵敏。它根本不看参考电平，只看麦克风自己：

1. **开头 1 秒取峰值当「回声基准」**（`seed_seconds`）。这段时间麦克风里要么是
   回声、要么是静音，不会是你说话，所以这 1 秒内不判断。
2. **之后只从「低于门槛」的帧里慢慢跟**，取这些帧的 p90（`base_percentile`）当基准。
   回声本身波动很大，门槛必须压过它自己的高分位（`margin` 再乘一档）。
3. **高于门槛的帧不算回声**——否则你一说话基准就被自己顶上去、越说越打不断；
   它们只用来攒时长：连续超过 `min_seconds` 才算插话。

好处是门槛天然带着「麦克风自己听到的回声有多大」，不依赖两个滑窗对得上，
音量变化、换扬声器、换房间都自己跟得上。

- 打断前有 1 秒滚动缓存，触发时把缓存先塞进断句器，不切掉开口的第一个字
- **播出去的电平按实时节奏写声卡**（40 毫秒一块边写边等）：一次把整段丢给驱动，
  播放会瞬间"写完"，打断也就停不下来了；按块写还能当场掐掉

| 配置（`[bargein]`） | 说明 |
| --- | --- |
| `enabled` | 语音自动打断总开关，**默认 false**（实测容易自我打断） |
| `key` | 按键打断用哪些键，默认 `"esc+enter"`；改成 `"esc"` 就只认 Esc |
| `min_seconds` | （以下只在 enabled = true 时生效）连续说多久才算插话，默认 0.25 秒 |
| `margin` | 比「麦克风里听到的回声」响几倍才算插话，默认 1.6；调大更稳、调小更灵敏 |
| `min_rms` | 绝对下限，压住底噪 |
| `seed_seconds` | 开头用多久校准回声基准，默认 1 秒 |
| `base_seconds` / `base_percentile` / `base_track` | 基准的跟踪窗长 / 分位 / 跟随速度 |

按键打断自己不靠任何检测：只在「正在说话」时才读键盘，所以它**不会吃掉你的
Ctrl+C**（一直读的话后台服务就退不出来了）；每轮开口前会先把积压的按键丢掉，
免得上一轮的残留把这一轮的开头打断。单测：`python scripts/test_hotkey.py`。

**自识别护栏**（不管走哪条路都在）：打断收到的音频如果转出来的文字和它刚刚
说过的话撞上了（完全包含，或长句相似度 ≥ 0.8），就直接丢掉、不回答，
只在日志里留一行 `[自识别] 这句像是我自己刚说的（…），已忽略`。
所以哪怕回声判定歪了，也不会出现「自问自答」的嵌套。

想验证这台机器会不会被自己的回声骗到（会外放三段话，**不用你说话**）：

```powershell
python scripts/test_bargein.py --echo    # ★ 只外放、人别出声：必须一次都不触发
python scripts/test_bargein.py           # 合成对照：回声不该打断、插话该打断
python scripts/test_bargein.py --live    # 真机回环：量回声 + 你自己真的插一句
```

> 本机实测：真实回声整段回放一次都不误触发；叠上合成人声（能量比回声响 4 倍以上）
> 能稳定在 0.5 秒左右打断。

**已知局限**：扬声器音量很大、你又离麦克风很近时，回声和你说话差不多响，
物理上就分不开（实测要盖过回声 4 倍能量才算稳）。这种场合用耳机最省心：
基准会跟到底噪附近，任何说话都能立刻打断。
另外，**刚开始用的第一句**要先攒够样本（大约前 0.3~0.5 秒）才能判断，
这一句里插话可能不生效；那句太短没攒够的话，下一句会接着攒。

## 6. 语调和断句（重点）

之前听起来「又平又顿」，根因有两个：

1. **Piper 的中文音色看不到标点。** 用 espeak-ng 的 `cmn` 声线时，
   `，。？！` 全部不会变成音素——把 `我们下午一起去西湖边散步，顺便买奶茶。`
   和去掉标点的版本分别音素化，结果**完全一样**。所以模型只能靠自己学到的韵律断句。
2. **原来的做法每个逗号就切一块**，每块单独合成、各自收尾，再在中间塞 150ms 静音。
   一句话被切成五六个碎片，每片都以「收尾降调」结束，听起来自然又平又碎。

现在的做法：

| 改进 | 效果 |
| --- | --- |
| 只在**句末**标点切；整句超过 60 字才退到逗号切 | 每块都是完整句子，模型能规划整句韵律 |
| 短于 14 字的句子与下一句**合并** | 不再出现「好的。」这种一秒钟的碎片 |
| 块间补白从 150ms 降到 80ms | 不再出现「说完一句停半天」 |
| `length_scale` 1.0、`noise_w_scale` 0.85 | 语速与起伏回到模型训练时的分布 |
| 不删句首的「好的，…」 | 开头不再突兀 |

同一句话的实测：**11.22s → 9.65s**，中间不再有 6 次做作的停顿。

想亲耳对比：

```powershell
python scripts/tts_probe.py --compare
# 生成 sessions\prosody_old_按逗号切块.wav 与 sessions\prosody_new_整句合成.wav
```

继续微调（`config.toml` 的 `[tts]`）：

| 参数 | 作用 |
| --- | --- |
| `length_scale` | 语速，1.0 最自然，1.05 更从容，0.95 更快 |
| `noise_w_scale` | 音长起伏，0.9~1.0 更有感情，0.7 更平稳 |
| `min_chunk_chars` | 调大 → 更连贯但更晚出声；调小 → 更早出声但可能碎 |
| `max_hold_seconds` | 攒句等待上限，保证短回答也能及时出声 |
| `inject_pauses` | `true` 时用 `[[,]]` 强行注入停顿音素，停顿更清晰但语气偏平 |
| `sentence_silence` | 块间补白，0 也可以 |

还可以直接看音素与停顿分布：

```powershell
python scripts/tts_probe.py --sweep          # 扫参数看语速
python scripts/tts_probe.py "你好[[,]]世界"   # 看注入停顿的效果
```

## 7. 实测性能（Core Ultra 5 225H + Arc 130T 核显）

| 环节 | 实测 |
| --- | --- |
| 本地技能（几点了 / 定闹钟 / 查课表） | **0 s**（正则直接命中，不调模型） |
| SenseVoiceSmall（5.6s 音频） | 0.08 s（RTF 0.014） |
| Whisper turbo int8（5.6s 音频）**CPU** | 3.3 s（RTF 0.59） |
| Whisper turbo int8（5.6s 音频）**Arc 核显** | **0.49 s（RTF 0.087，快 6.8 倍）** |
| Whisper 首次在核显上编译图 | 约 10 s（只在第一次，之后有缓存） |
| Piper 合成 | RTF 0.04~0.07，首块 0.12 s |
| **ZipVoice 克隆合成（当前默认）** | **RTF 1.1~1.4，首段 1.4~2.7 s**（参考 10 s / 4 步，CPU） |
| qwen3.5:4b 生成 | **17.6 tok/s**（qwen2.5:7b 是 12.3） |
| qwen3.5:4b 热首字 | 0.5 s（冷启动加载 3.4 GB 约 4 s） |
| **端到端首音** | **0.7 ~ 2.1 s（Piper）/ 2~5 s（克隆）** |

优化建议，按收益排序：

1. **Whisper 走核显**（默认 `[asr] whisper_device = "auto"`，有 Intel 核显就会用上）：
   实测 3.3 s → 0.49 s。想看自己这台快多少：`python main.py gpu --bench`。
2. `keep_alive = "30m"` + 先跑一次 `selftest`，避免模型反复加载。
3. `strategy = "sensevoice"`：中文短句场景直接砍掉 Whisper 的 1~3 秒。
4. 想更快可以让 Whisper 走 openvino-genai（需要 stateful 导出）：
   ```powershell
   optimum-cli export openvino --trust-remote-code --model openai/whisper-large-v3-turbo `
       --weight-format int8 whisper-large-v3-turbo-int8-ov-stateful
   ```
   当前模型是 `--disable-stateful` 导出的，GenAI 的 `WhisperPipeline` 会报
   `beam_idx not found`，所以代码走的是 Optimum 路径（会自动识别并提示）。
5. 纯 CPU 跑模型时调 `[llm] num_thread`（线程数）/ `num_batch`（预填批大小）。
6. 换更小/更快的模型：`python scripts/bench_llm.py <模型名>` 先体检一遍（见下节）。

### 7.1 换模型怎么选（实测对比）

一条命令就能给候选模型做体检（延迟 / 是否在思考 / 看图识字）：

```powershell
python scripts/bench_llm.py qwen3.5:4b qwen2.5:7b                 # 横向对比（会来回换模型）
python scripts/bench_llm.py qwen3.5:4b --vision-sizes 768,1024,1568
python scripts/eval_router.py --builtin --model qwen3.5:4b        # 选工具准不准
python scripts/test_dialog.py --no-tts --model qwen3.5:4b "用一句话介绍杭州"   # 看回答质量
```

本机（Core Ultra 5 225H + Arc 130T 核显）实测：

| | **qwen3.5:4b**（现在用） | qwen2.5:7b（老的） |
| --- | --- | --- |
| 体积 | **3.4 GB** | 4.7 GB（看图还要另装 3.2 GB 的 qwen2.5vl:3b） |
| 生成速度 | **17.6 tok/s** | 12.3 tok/s |
| 预填速度 | 284 tok/s | **345 tok/s** |
| 冷启动首字 / 热首字 | 4.4 s / 0.5 s | **2.9 s** / 0.1 s |
| 看图（1024 长边） | **自带**，7.3 s，5/5 关键词都认对 | 不支持；qwen2.5vl:3b 是 8.2 s，5/5 |
| 工具选择 | 8/8（`test_tools --live`）、评估 18/23 条调工具、闲聊不乱调 | 7/8；评估 17/23 |
| 回答风格 | 更像凯尔希、更简洁（「你」） | 偏通用，爱用「您」 |

工具那一段值得多说一句：4b **不带思考时对「该不该调工具」略迟钝**
（「我的备忘里有什么」竟然直接凭印象答、不查），所以我把 `voice_loop/tools.py` 里的
`TOOL_HINT` 写成了**机械的关键词白名单**（出现 日程/提醒/备忘… 就先查一遍）。
改完之后 8/8，而且指代类的（「那件事是什么时候」）也会先去查了。

**为什么换**：一个模型同时管文本和看图（7.9 GB → 3.4 GB）、生成快 40%、
中文和人设都更贴。代价是首字慢 0.4 s（两边都在 1 s 以内）、预填慢 18%。

★**最大的坑：thinking**★。qwen3.5 默认**先默默想一两千字再开口**——同一次回答
总耗时 15.8 s，关掉思考后 5.6 s，而这十几秒用户只能干等。所以配置里有：

```toml
[llm]
think = "off"     # off = 发 think=false；on = 显式打开；auto = 不传，交给模型默认
```

换任何带 thinking 的新模型（qwen3*、qwen3.5* 这类），第一件事就是让 `bench_llm`
看一眼汇总表里那一列「思考」，再决定 `think` 写什么。

> 想上更大的模型（比如 `qwen3.5:9b`）？**先看下一节**：实测它在语音场景是退步，
> 不是升级。

### 7.2 要不要上更大的模型（9b 实测：不建议）

`qwen3.5:9b`（6.6 GB）看起来是「同系列更大一档」，本机实测却**在语音场景全面变差**：

| | qwen3.5:4b（默认） | qwen3.5:9b |
| --- | --- | --- |
| 体积 | **3.4 GB** | 6.6 GB |
| 生成速度 | **17.6 tok/s** | 8.5 tok/s（慢一倍） |
| 预填速度 | **284 tok/s** | 189 tok/s |
| 热首字 / 首轮预填 | 0.5 s / 2.0 s | 0.6 s / 2.6 s |
| 看图（长边 1024） | **7.3 s** | 16.5 s |
| 工具选择（`test_tools --live`） | **8/8** | 5/8 ← 更差 |
| 思考（默认开着） | 1122 字 / 15.8 s → 5.6 s | 1132 字 / 31.9 s → 15.0 s |
| 回答风格 | 简洁、够味 | 更丰富，但也更长（语音里更费时间） |

9b 最反直觉的一点是**工具选择反而掉到 5/8**（「记一下买牛奶」「叫我起床」
「我的备忘里有什么」它都不调工具，直接凭印象答）。它更像「重思考型」模型：
不带思考时倾向直接开口，而不是先去查。所以想上 9b 的话，得把
`[llm] think` 改成 `on`（那样每次回答又要多等十几秒），否则**功能上是退步**。

结论：**默认留在 4b**。真想上更大的模型，先跑这两条命令再决定：

```powershell
python scripts/bench_llm.py <模型>              # 生成/预填/首字/看图，四项一眼看完
python scripts/test_tools.py --live --model <模型>   # 工具选择会不会退步
```

### 依然能再快一点

- **纯 CPU 调参**：`[llm] num_thread = 6~10`（本机 14 核）、`num_batch = 512`，
  以及把 `[llm] num_ctx` 从 4096 降到 2048（上下文越小预填越快）。
- **换成更小的模型**：`qwen3.5:2b` 已经装在机器上（2.7 GB，更快但人设/工具会差些），
  `qwen3.5:0.8b` 更小；换之前先 `python scripts/bench_llm.py qwen3.5:2b` 量一下。

### 不打算做的

- **NPU 跑 Whisper**：会崩，已写进测试（`scripts/test_accel.py` 断言 auto 不选 NPU）。
- **TTS 上 GPU**：Piper 是 RTF 0.04，加速收益远小于折腾成本；
  克隆后端（ZipVoice）CPU 上 RTF 1.1~1.4，是目前唯一值得折腾的加速位，
  但 sherpa-onnx 的例子只给了 `provider="cpu"`，能不能走 OpenVINO / 核显还没验证。
  `[tts] use_cuda` 只对装了 CUDA 版 onnxruntime 的机器有用，配错时 `main.py gpu` 会提醒你。

### 为什么值得这么拆

1. **加能力域不用动 pipeline**：写一个 `mcp/servers/xxx.py`，在 `config.toml` 的
   `[[mcp.servers]]` 里登记一行就完事。以前加一类工具要改 `tools.py` 的 spec 表、
   handler 表、pipeline 的分发，三处。
2. **同一份 handler，两条路都能用**：`python -m voice_loop.mcp.serve skills` 就是把
   助手自己的日程/备忘能力交给 Copilot / Claude Code 用（见下面配置）。
   反过来接别人的服务器（`mcp-server-git` 之类）也是同一个宿主。
3. **崩了不连坐**：每个服务器一个连接，`stdio` 模式下还是独立进程；
   某一台挂了只让这一路失败，宿主会顺手把它拉起来。
4. **能单测**：协议层、服务器、宿主都能脱离模型测（`scripts/test_mcp.py`）。

### 写设定时踩过的坑（实测）

| 现象 | 原因 | 怎么办 |
| --- | --- | --- |
| 机器人复读同一句话 | 示例台词里写了「你常问的问题 + 它的完整答案」，场景和用户原话一模一样，小模型就当成查表 | **别把常问问题的完整答案写进 `lines`**；写口吻、称呼习惯、不易撞车的情景 |
| 用第三人称描述自己（「罗德岛的医疗主管凯尔希正在……」） | 只给 `background` 时，模型把它当百科条目念 | 提示词里已硬性要求「用第一人称、不要自我介绍」；`background` 也尽量用「你/我」写 |
| 提示词越长越容易走形 | 字段堆太多 | 优先写好 `background` + 3~5 条 `style` + 2~3 条 `lines`，`avoid` 只留真正在意的 |

> 索引文件开头的 `_字段说明` 就写着每个键的意思，改的时候不用翻文档。
> 旧版（两个角色都写在 `characters.json` 里）用 `python main.py persona --split` 一键拆开。

### 换成角色本人的音色（零样本克隆，实测）

上面那条路只能换成「另一个 Piper 音色」。想要**凯尔希本人的音色**，用的是零样本克隆：
给一小段她的语音（参考音频）+ 这段语音的逐字文本，模型就用她的音色读中文。**这是当前默认后端。**

后端已经接好，用的是**本机早就装着的 sherpa-onnx**（不用 torch、不用 CUDA、不加新运行时）：

```powershell
python scripts/download_models.py --only zipvoice    # 156 MB（模型 104 + 声码器 52）
python scripts/tts_clone_probe.py --ref data/personas/kalsit/任命助理.wav --compare
```

```toml
[tts]
backend = "zipvoice"                                  # 默认：用角色本人的音色；改回 "piper" 即还原
clone_audio = "data/personas/kalsit/任命助理.wav"      # 参考音频（5~15 秒、单人、无背景音乐）
clone_text = ""                                       # 留空 = 同名 .txt，再没有就本地 ASR 自动转写
clone_steps = 4                                       # 4 最快；8 慢一倍；16 慢三倍，音质提升有限
clone_max_seconds = 10.0                              # 参考音频截取上限，见下表
```

两个后端都不会哑：克隆模型没装全、或参考音频不可用时会**自动退回 Piper 出声**
（`main.py selftest` 与 `create_tts` 都会把原因打出来）。

角色文件里也能各配各的（`voice_ref` / `voice_ref_text` / `voice_model`），切换角色时**当场换音色**，
不用重启：只换参考音频就直接换；换**模型目录**（微调过的角色声线）就卸载重载，
下次说话时用她自己的模型。没配的角色自动切回 `[tts] clone_dir` 的默认模型——
这样「一个角色换过声线，别人跟着遭殃」不会发生。

#### 零样本克隆的实测数据（Core Ultra 5 225H，纯 CPU）

同一句话（「我在，博士。今天的日程已经排好了。」14 个汉字）换不同参考音频的效果。
**中文自然语速约 3.5~4 字/秒**，所以「字/秒」这一列直接就是语速是否正常的客观指标：

| 参考音频 | 参考时长 | 输出时长 | 语速 | 首段出声 | RTF |
| --- | --- | --- | --- | --- | --- |
| 信赖触摸 | 4.5 s | 2.84 s | 4.92 字/秒（偏快） | 1.43 s | 0.50 |
| **干员报到（当前默认）** | 7.7 s | 3.93 s | **3.56 字/秒（自然）** | 2.4 s | 0.68 |
| 新年祝福 | 12.2 s | 3.72 s | 3.77 字/秒（自然） | 3.9 s | 1.05 |
| 交谈1 | 13.7 s | 3.62 s | 3.87 字/秒（自然） | 4.0 s | 1.11 |
| *Piper 对照* | — | 4.94 s | — | **0.10 s** | **0.05** |

两条结论：

- **语速是参考音频定的，不是参数定的。** 参考越短它说得越快（4.5 s 的参考 → 4.9 字/秒），
  7~14 s 的参考最自然。想换语速，就换一条参考音频。
- **`clone_speed` 两边都不安全，别用它调语速**：>1 时实测 1.15 → 输出从 3.62 s 掉到
  **1.37 s（10.2 字/秒，已经含糊）**；<1 在**微调模型**上会退化成「又快又吞停顿」
  （0.90 → 整句 0.53 s / 7.55 字/秒、逗号停顿直接消失）。它只在出厂蒸馏模型上表现正常，
  **换模型后必须重量**。想放慢请用 `trim_min_gap_ms`（只插静音、不改音高），见下面
  「短句『太赶、停顿太短』怎么治」。代码里已夹到 0.5~1.0（防呆，但不保证好听）。

步数：4 步最快；8 步慢一倍，**输出时长一模一样（实测重复 4 次极差 0.00 s）**，所以默认 4 步。
另外**唤醒后的第一句还要多等约 2 s**——克隆模型是唤醒时才加载的（待机时释放，不占内存）。

#### 三条硬约束（都实测踩过）

1. **参考文本必须和音频逐字对应。** 这是「有概率乱说」的真正原因——不是随机，是**错配**：
   同一配置重复跑 4 次输出时长极差 0.00 s，完全确定性；一旦文本和音频对不上（比如
   21 秒的音频被截成 10 秒却仍配着整段文本），就会说成含糊的一串。
   所以规则是：**文本来自文件（同名 `.txt` / 同目录清单）→ 音频一律不截**；
   没有文本（靠自动转写）→ 先截到 `clone_max_seconds`，再拿截完的音频去转写，两边自然一致。
2. **参考音频要单人、干净、7~14 秒**。首尾静音会自动掐掉；背景音乐会让音色飘。
3. **它只认中文和英文**。日语参考见下一小节（有绕法，但中文参考效果最好）。

#### 参考文本从哪来（三种，按优先级）

1. `[tts] clone_text` 或角色文件里的 `voice_ref_text`（写死在配置里）
2. 音频同名 `.txt`（如 `干员报到.txt`）
3. **同目录的清单文件**（实测素材就长这样：一行文件名 + 空行 + 一段文本，见
   `data/personas/kaltsit/kaltsit.txt`，38 条全能对上）
4. 都没有 → 用本机 SenseVoice 自动转写，并把结果缓存成同名 `.txt`（不对可以直接改）

清单格式（也认 `文件名<TAB>文本` 这种一行搞定的写法）：

```
任命助理

博士，请坐。别紧张，我只是来查看你的身体状况。……

交谈1

我会定期为你进行理学检查，记录你的生命征象与意识状态……
```

#### 日语参考音频怎么办（现在用不着了，但留着）

最初的素材是凯尔希的日语原声。直接喂进去会这样：

```
Ignore OOV 'ド'   →   Failed to convert prompt text 'ドクター' to token IDs
```

假名被当前端 OOV 丢掉，输出退化成**复读乱语**——一句 17 字的中文，生成了 22.6 秒音频（正常 3 秒）。

绕法：**把日语转成罗马字**，前端就当英文词、交给 espeak 念，和原音基本对得上：

| 参考文本 | 输出时长 | 结论 |
| --- | --- | --- |
| 日语原文（自动转写） | 0.08 s | 前端直接报错，废 |
| 空文本 | 22.59 s | 退化，复读乱语 |
| 中文意译 | 16.05 s | 退化 |
| **罗马字（`dokutaa kakete…`）** | **3.11 s** | 能出声，但语速偏快、偶尔含糊 |

所以本项目的做法是：**SenseVoice 转写 → pykakasi 转罗马字 → 喂给 ZipVoice**，全自动
（`clone_romanize = true`，依赖只有一个纯 Python 的 `pykakasi`）。
**但后来换成了凯尔希的中文配音**：同一角色的中文音色本来就是目标音色，而且省掉整个
罗马字环节，语速和咬字都正常得多——所以现在默认用中文素材。

#### 为什么不用 `IndexTTS-2.5-MNN`

你提到的这个项目，GitHub 上**搜不到**（`index-tts mnn` 是 0 条结果）。现状是：

- IndexTTS 是 2.4 万星的官方项目，确实支持跨语种克隆，但它是 **PyTorch + 多 GB 权重**，
  且官方中文前端依赖 `pynini`——**Python 3.13 没有 wheel**（实测 `No matching distribution found`），
  要跑得专门建一个 3.12 环境、再下几个 GB。CPU 上 RTF 未知，大概率比 1.4 更慢。
- MNN 系的项目（`mnn-tts`、`Bert-VITS2-MNN`、`CosyVoice3-MNN`…）基本都是**给 Android 用的
  C++ 工程**，Windows 上要自己编；而且没有哪个是「IndexTTS-2.5 的 MNN 版」。

ZipVoice 这条路的好处是：**运行时本机早就装好了**（sherpa-onnx 自带它）、模型 156 MB、
不碰 torch、CPU 就能跑，实测 RTF 1.1~1.4。代价是文本前端只认中英文——所以有了上面那段罗马字绕法。

> 说在前面：**音色像不像只能用耳朵判断**。`scripts/tts_clone_probe.py` 会把生成结果写成
> `sessions/tts_clone_probe/*.wav`，跟 Piper 的同一句话放在一起。
>
> 现在默认就是克隆音色。它换来的是「像她」，代价是「说多久、等多久」——
> 一句话 2 秒就得等 2.5 秒才出声。想让对话更干脆，把 `[tts] backend` 改回 `"piper"`，
> 改一行就生效，其余什么都不用动。

### 克隆音的「语速不稳」其实是死静音（实测）

听着像忽快忽慢，量出来却是模型**每段开头塞了 0.58~1.48 秒纯数字静音**
（参考音频自己只有 0.04s，且长度随机，实测 8 句：0.58/0.99/1.04/1.14/1.18/1.25/1.32/1.48s）。
发音速率本身很稳：**5.88~7.48 字/有声秒，相对参考 0.91~1.16×**。
去掉死静音后：首段出声提前 0.7~2.0 秒，中位语速 3.77 → 4.78 字/秒，
3 句回答的音频从 10.18s 缩到 8.07s。

```toml
trim_output_silence = true   # false = 完全用模型原始输出
trim_lead_ms = 40            # 开头保留的静音（别设 0，免得第一个字被啃）
trim_tail_ms = 80            # 结尾保留的静音
trim_max_pause_ms = 0        # 0 = 不动句内停顿（默认）；>0 = 压缩超长停顿
trim_min_pause_ms = 260      # 压缩时的下限
trim_min_gap_ms = 240        # ★句内停顿短于它就拉长到它（只是插静音，不改音高）★
trim_min_gap_floor_ms = 60   # ★只拉长「本来就 ≥ 这个长度」的空隙（别设 0，见下）★
first_chunk_max_chars = 16   # ★首块最多几个字★（0 = 不限，见「为什么偶尔卡一下」）
```

句内停顿默认不动（**要压只能设 ≤450，实测单次停顿都不到 0.6s，设 600~1200 完全无效**）：
设 `trim_max_pause_ms = 450` 后中位语速 4.78 → 5.68 字/秒、长/短比 1.39 → 1.25×，但整体偏快。
裁剪逻辑见 `voice_loop/tts/pacing.py`，测试 `python scripts/test_trim_pacing.py`。

#### 短句「太赶、停顿太短」怎么治（实测）

用户反馈「说『我在，博士』时『我在』太快，而且『我在』和『博士』之间间隔太短」。
量出来是这样（微调后的凯尔希，逗号处）：

```
静止40ms → 声「我在」220ms → 静止60ms ← 逗号只停 60ms（人类要 200~400ms）
→ 声「博士」360ms → 静止90ms      合计 0.80s / 5.00 字/秒
```

人类平稳语速约 **3.5~4.5 字/秒**。两个旋钮试过：

| 档位 | 时长 | 字/秒 | 逗号停顿 | 结论 |
|---|---|---|---|---|
| 现状 | 0.80s | 5.00 | 60ms | 太赶 |
| `trim_min_gap_ms = 180` | 0.92s | 4.35 | 180ms | 好 |
| **`trim_min_gap_ms = 240`** | **0.96s** | **4.17** | **240ms** | **默认选它** |
| `trim_min_gap_ms = 300` | 1.02s | 3.92 | 300ms | 偏慢 |
| 叠加 `clone_speed = 0.95` | 0.97s | 4.12 | 240ms | 几乎无变化（这个旋钮不灵） |
| 叠加 `clone_speed = 0.90` | **0.53s** | **7.55** | **80ms** | ★**崩了**★ |

**结论：放慢用 `trim_min_gap_ms`，别用 `clone_speed`。** `clone_speed < 1` 在微调模型上会
退化成「又快又吞停顿」（0.90 → 7.55 字/秒、逗号停顿消失），跟 `>1` 坏掉是同一类现象；
它只在出厂蒸馏模型上表现正常，换模型后必须重量。拉长停顿只是插静音，不动音高，安全得多。

#### ★但 `trim_min_gap_ms` 无差别套用会「卡顿」★（两个角色都会，跟哪个模型无关）

用户反馈「两个角色声线都明显卡顿」。隔离量出来的原因就在这个旋钮：
**它会把字与字之间 10~40ms 的自然音渡也撑成整齐的 240ms**——每个字之间都垫一段
等长静音，听起来就是一顿一顿。同一段音频（原声空隙 `[10, 70, 890, 20, 40, 10, 850, 10, 20, 30, 110]`）：

| 设置 | 音频 | 空隙变成 |
|---|---|---|
| `min_gap_ms = 0` | 6.41s | 原样保留 |
| `min_gap_ms = 240`（无门槛） | **8.25s** | 11 个全变 240ms ← 白加 1.84s 死气 |
| `min_gap_ms = 240` + `floor = 60` | **6.58s** | `[1020, 10, 40, 880, 20, 240]` 只动真正的停顿 ✓ |

所以加了**门槛** `trim_min_gap_floor_ms`（默认 60）：只有本来就 ≥ 门槛的空隙才拉长，
音渡一律不动。阿米娅实测：8.34s（旧）→ **7.45s**（新）。
测试断言的这一点：`python scripts/test_trim_pacing.py`（43 项，含「30ms 微空隙不动」）。

#### ★为什么偶尔会「卡一下」（实测定位）★

两件事，都是克隆后端特有的：

**① 每次合成调用都要重新编码一遍参考音频**（开销 ≈ **0.36 × 参考秒数**）。
凯尔希微调模型，同一句「嗯。」：

| 参考音频 | 长度 | 合成耗时 | 固定开销 |
|---|---|---|---|
| 干员报到.wav | 7.79s | 3.27s | **2.82s** |
| 行动开始.wav | 2.51s | 0.97s | 0.58s |
| 问候.wav | 0.54s | 0.30s | ~0s |

→ **参考别用 8 秒的，用 4 秒左右**。实测换成 ~4 秒的参考后（凯尔希 精英化晋升1 3.91s、
阿米娅 行动失败 4.11s），同句 RTF **1.16 → 0.78**、固定开销 3.6 → 0.96s，
而且 RTF < 1 之后**播放队列再也不会饿死**（句间空档 +1.35s → **0.00s**）；
代价是节奏会变一点（音频时长 ±10%），两边都写了 A/B 试听再定。

**② 第一块攒太长 → 开口前先干等**。ZipVoice 是「整块生成完才回音频」，
首块 60 字（约 8 秒音频）= 开口前先等 8 秒。给首块单独设上限就好了：

```toml
first_chunk_max_chars = 16   # 首块最多 16 字，一到句末就切（后面几块不受影响）
```

实测同一段回复的开口等待：凯尔希 **8.08s → 1.91s**，阿米娅 **8.67s → 2.10s**，
而且后续每一段的队列空档都是 **0.00s**。
（默认 0 = 保持老行为；Piper 那边「短句与下一句合并」是特意调过的，不能被这条改掉。）

#### 三个必打的补丁（`finetune_zipvoice.py` 会自动打，幂等、留 `.py.orig`）

1. **官方训练脚本硬编码单线程**：`train_zipvoice.py` 的 `__main__` 里
   `torch.set_num_threads(1)`，于是 `OMP_NUM_THREADS` 完全无效——实测 14 核机器上
   **只跑 0.97 核**。改成读 `ZIPVOICE_NUM_THREADS` 后 **9.32 核**（同一份验证工作 180s → 78s）。
2. **torch ≥2.9 的 onnx 导出器不收 `dynamic_axes`** → 加 `dynamo=False` 走 TorchScript。
   ★只匹配 `torch.onnx.export` 内部那两行★，否则会传给包装函数并报
   `got an unexpected keyword argument 'dynamo'`。
3. **i18n/依赖三连**：`PYTHONUTF8=1`（官方读 TSV 没写 encoding，Windows 默认 GBK 直接崩）、
   `lilcom`（写 fbank 特征）、`onnx` + `onnxruntime` + `onnxscript`（导出与 int8 量化）。

| 数据 | 38 条 / 4.8 分钟 → 30 对可用（8 条 <0.8s 的极短音被过滤，只占 1.6% 时长） |
| `piper_phonemize` / `k2` | ✓ 都有 cp313 win_amd64 轮子（那页 4385 个轮子里 1079 个是 `win_amd64`，**别再以为只能 Linux**） |
| 版本对齐 | torchaudio 的 CPU index 上 cp313 只到 2.11 → **torch/torchaudio/k2 全用 2.11**（k2 要选 `torch2.11.0` 那个轮子） |
| 训练速度 | 42.6 秒/iter（含验证），**1 epoch ≈ 3.4 分钟**；100 iter ≈ 21 epoch ≈ 1.2 小时 |
| lhotse 两个硬壁垒 | 训练桶数默认 30 > 我们的 27 条 → 必须 `--num-buckets 8`；**验证 sampler 源码里没传 `num_buckets`**，走默认 10 → 验证集必须 ≥10 条 |
| checkpoint | 每个 **1.87 GB**（含优化器状态）→ `--keep-last-k 3`，否则几十 GB |
| 凯尔希结果 | 训到 epoch 9（checkpoint-60）时崩在 `0xC0000005`（Windows 访问违例，原因未定位）；**用 checkpoint-60 导出照样能用**，sherpa-onnx 实测加载+合成正常，token 表与出厂模型逐字节相同 |
| 阿米娅（第二个角色） | 38 条 → 35 对 / 227.5 秒 → 78 iter，**12.4 秒/iter、16.1 分钟跑完，一次没崩**；平均(avg=2)→ 导出 → 安装一步过，token 表同样一致。RTF 实测 1.2（出厂 0.7 那档）。A/B 同句同参考：「博士，我在。」出厂 9.09 字/秒 vs 微调 **5.97 字/秒**（更像人），长句 3.14 → 3.33 字/秒、句内停顿 ~240ms |
| 代价 | 导出的是**非蒸馏**模型 → 比出厂蒸馏版慢 2~3 倍（实测 RTF 2.18 vs 0.74，同参考音频，所以「更像她」是要拿时间换的） |
| 听感 | A/B 实测（同句同参考）：**微调版更像人类的节奏**，出厂版偏机械 |

## 15. 2026-09 声线调优实录：沙沙声 / 卡顿 / 人名

这一节记的是最近一轮「声音听着怪」的完整定位过程——**三次判断、两次靠量测纠正**，
留着当方法论看比只看结论更有用。

### 15.1 克隆后端的三条硬事实（都是量出来的）

**① 每次 `generate()` 都会重新编码一遍参考音频**，开销 ≈ **0.36 × 参考秒数**：

| 参考音频时长 | 合成「嗯。」耗时 | 固定开销 |
|---|---|---|
| 7.79s | 3.27s | **2.82s** |
| 2.51s | 0.97s | 0.58s |
| 0.54s | 0.30s | ~0s |

翻过 sherpa-onnx 1.13.8 的 API：`OfflineTts` 只有 `generate / num_speakers / sample_rate`，
`GenerationConfig` 只能**每次调用**传参考，`OfflineTtsZipvoiceModelConfig` 里没有参考字段
→ **没法规避、也没法预编码缓存**（所以参考越长，每次合成就越贵）。

**② 参考音频不只给音色，还给韵律**。微调之后音色主要来自权重（换个普通参考她还是很像），
但**节奏、情绪、音量起伏仍然跟着参考走**。实测教训：把参考换成
「越是强大越是脆弱…」（冷冽念白）、「我没事的……大家，请振作起来！」（激动 + 长停顿）
之后，输出出现发抖/发毛——**挑参考不能只看时长，要看内容是否平静**。

**③ 首块多长 = 开口前等多久**。ZipVoice 是「整块生成完才回音频」，首块 60 字（≈8 秒音频）
就是等 8 秒才出声。

### 15.2 「卡顿」的两种成因（以及一个我自己算错的公式）

线上时序：`_speak_chunk()` 逐块合成，合成完一块就交给播放队列；播放是实时的。
所以**第 i 块的音频要到「累计合成耗时」才可用**，而第 i-1 块早就播完了 → 中间一段静音。

正确公式：`空洞 = max(0, 累计合成耗时 − (累计已播时长 + 首块等待))`

| 配置 | 开口等待 | 空洞 |
|---|---|---|
| 8 秒参考 + 首块不限（长块） | 8.01s | **0.00s** |
| 4 秒参考 + 首块不限 | 4.42s | 0.00s |
| **首块限到 16 字** | 1.91s | **3.48s** ✗ |

> ★踩的坑★：探针一开始写成「本块合成耗时 − 本块音频长度」，于是「首块短、下一块长」时
> 报 0.00s 空洞，实际是一段 3.48 秒死气。**要短块就必须所有块均匀地短**，只短第一块必然
> 留空洞——`first_chunk_max_chars` 因此默认 0（关）。这类时序量算完，务必拿
> 「首块特别短」这种极端情形自检一遍。

### 15.3 「沙沙声」的客观指标：高频能量占比

同一句话、同一参考，量 `>6kHz 能量占比`（沙沙声）与有声帧 RMS 波动（音量抖）：

| 模型 | 步数 | 高频占比 | 音量波动 | RTF |
|---|---|---|---|---|
| 凯尔希 出厂蒸馏 | 4 | **8.20%** | 5.70dB | 0.55 |
| 凯尔希 微调（非蒸馏） | 4 | 10.52% | 5.33dB | 1.16 |
| 凯尔希 微调 | 16 | 8.89% | 5.23dB | 4.41 |
| 阿米娅 出厂蒸馏 | 4 | **12.99%** | 5.20dB | 0.52 |
| **阿米娅 微调（非蒸馏）** | 4 | **35.86%** | 4.76dB | 1.09 |
| 阿米娅 微调 | 16 | 21.88% | 4.68dB | 4.42 |

结论：**非蒸馏模型 int8 量化后的高频噪声明显高于蒸馏模型**（阿米娅是基准的 2.8 倍）；
加步数能压一点，但 16 步 RTF 4.4、32 步 RTF 8.9，**代价不可接受**。
→ 下一步方向是「重新导出 fp32（不量化）再比」，而不是加步数。

### 15.4 ASR 对少见人名不敏感：拼音音近校正

用耳听攒下的 65 条听错评估（凯尔希 58 + 阿米娅 7）：拼音全同 20、近音 28、
名字带后续词 4、两字缩写 4、昵称/字母 9。方案 = **别名表（精确）+ 拼音音近推广**，
命中就把那段字改回规范名，于是唤醒匹配、对话里的称呼、送给大模型的正文三处一起受益。

规则（每条都是拿实测假阳性换来的）：

| 规则 | 挡住的反例 |
|---|---|
| **只在句首认**（名字 + 请求的说话习惯） | `海尔洗衣机`（海尔洗 ≈ 凯尔希的拼音）、`米亚的论文`、`开尔文是谁` |
| 近音**只允许第一个音节不同**（听错都错在首字：凯/开/海/太/台/泰/卡/费/佩） | `胎儿心率`（末字 心 ≠ 希） |
| 同韵母要求韵母 ≥2 字母（单人韵母太常见） | `阿米巴原虫` → 阿米娅 |
| 缩写（凯西/开西）后面必须是停顿或句末 | `开尔文是谁` 里的「开尔」 |
| 拼音撞车走黑名单 | `海尔洗` |

实测：汉字别名 59/59 全中、表外新听错 8/8 认出、22 条日常负样本 0 误改
（`python scripts/test_names.py`）。

### 15.5 这一轮的方法论教训

1. **音色/节奏类改动，一律先出 A/B 试听再改配置**——观感无法从数字推断，两次「按长度挑
   参考」都翻车了。
2. **覆盖参数名会写出永远成立的条件**：`match()` 里把算出的相似度又赋回参数 `ratio`，
   条件变成 `x >= x`，连「今天天气不错」都算唤醒命中——被已有测试抓住。
3. **量测公式本身要拿极端情形自检**（见 15.2），否则会得出与听感相反的结论。
4. 每次「以为找到原因」都先问一句：**有没有可能是另一处**？这轮三次归因，前两次
   （参考长度、参考情绪）都不是主因；第三次（量化）当时看着很像，**紧接着也被第 16 节
   的对照实验推翻了一半**——所以这条规矩的真实版本是：**没有对照实验，归因只能算猜想**。

## 16. fp32 导出 + 平台适配 + 可部署性自检（最新）

这一节两件事：把 15.3 的归因**做完闭环**（结论被推翻了一半），
以及为了让它能搬到别的机器 / 别的系统上跑，做了一轮平台梳理和一份只读自检。

### 16.1 fp32 到底有用吗？——第三个归因也被量测推翻了

15.3 的结论是「沙沙声主要来自 **int8 动态量化**」，所以这一轮做了对照实验：
把两个角色重新导出成 fp32，其余条件（参考音频、文本、步数、线程、机器）全部不变。

顺带发现一件早该知道的事：**官方 `onnx_export.py` 每次都会同时产出 int8 和 fp32 两份**
（`text_encoder.onnx` + `text_encoder_int8.onnx`），以前的安装步骤只认 int8 那份，
所以 fp32 一直是白导出来又被扔掉的。这一轮给安装步骤加了 `--precision`。

凯尔希 · 短句「我在，博士。」· 同参考 · 同一台机器：

| 模型 | 精度 | 步数 | 高频占比 | 音量波动 | 合成耗时 | RTF |
|---|---|---|---|---|---|---|
| 出厂（蒸馏） | int8 | 4 | **6.13%** | 5.54dB | 2.26s | 3.02 |
| 微调（非蒸馏） | int8 | 4 | 16.56% | 5.31dB | 4.36s | 5.60 |
| 微调（非蒸馏） | **fp32** | 4 | **15.60%** | 5.20dB | **8.33s** | 10.82 |

结论（三条，都反直觉）：

1. **fp32 只把高频噪声从 16.56% 降到 15.60%（−6%），代价是耗时翻倍**（4.36s → 8.33s）
   → 当时据此写下「量化不是沙沙声的主因」。
   ★**这一条当天下午就被 16.7 修正了**★：它是拿**单点**测量比出来的，而单点噪声极大
   （同配置只换采样步数，高频占比能从 3.89% 跳到 13.61%）。用配对法重算（4/8/16/32 步
   逐档对比），fp32 确实更低——凯尔希长句 4/4 档更低、平均 −2.6 个百分点。所以准确说法是：
   **量化有影响（约 −25% 相对值），但远不是主因。**
2. 真正的大差距在**模型本身**：出厂蒸馏 6.13% vs 微调 16.56%，**2.7 倍**。
   也就是说，噪声大是「非蒸馏基座 + 三百轮不到的微调」带来的，换精度治不了。
3. 「出厂蒸馏」这个对照还说明：**这套后端本来是可以很干净的**——问题不在 sherpa-onnx，
   也不在参考音频，而在我们喂给它的权重。
   ★这一条也被 16.7 推翻了★：清白的不是权重，权重只是**学着素材的样子**；
   真正的源头是**素材底噪**（安静帧高频占比：凯尔希 7.6% vs 阿米娅 36.4%）。

> ★这一轮最值钱的一行★：`fp32 相对 int8 只差 6%` 这一行对照，比前面所有推理加起来都管用。
> 归因类的结论，一律要用**只改一个变量的对照实验**闭环，否则很容易停在「听起来挺有道理」。

> 顺带记一个坑（下一轮会碰）：两条参考文本里都有 `……`，而 sherpa-onnx 的
> `matcha-tts-lexicon` 会把它当 OOV **丢掉**（日志里 `Ignore OOV '…'`）。
> 症状不重（省略号对应的那点停顿本来也不建模），但官方文档写着「参考文本必须逐字一致」，
> 所以「把 `…` 换成 `。`」是下一个免费的实验对象。

完整表格（两个角色 × 两种文本 × 两种精度 × 4 种步数）见 `sessions/ab_clone/report.txt`，
生成脚本 `scripts/ab_clone_model.py`（随跑随出 wav 与指标表）。

### 16.3 平台适配：换到 Linux / macOS 会怎样

代码里的平台差异本来就不多，这一轮把它们**收敛到两处**（`system_ops.py` 与
`tts/precision.py`），其余按平台分支的地方都补了明确话术。改动前后对照：

| 位置 | 之前 | 现在 |
|---|---|---|
| `voice_loop/system_ops.py` | 只有 Windows 实现，其它系统一律「暂不支持关屏」 | Windows（`SC_MONITORPOWER`）/ Linux-X11（`xset dpms`）/ macOS（`pmset`、`caffeinate`）三套；**Wayland 明确说「做不到」并给出该按什么**，不假装成功 |
| `main.py listen -B` 后台服务 | POSIX 上传 `creationflags=0`，终端一关就被 SIGHUP 带走 | POSIX 用 `start_new_session`；日志查看提示按平台给 `tail -f` / `Get-Content` |
| `vision.py` 截屏 | `ImageGrab.grab()` 不传 `xdisplay` → Linux 上必失败（它不读 `$DISPLAY`） | Linux 自动带上 `$DISPLAY`；剪贴板读图在非 Windows/macOS 上回一句人话（Pillow 没实现） |
| `accel.py` | Ollama 日志路径写死 `~/AppData/Local/…`，iGPU 开关没判平台 | 路径按平台推（Linux `~/.ollama/logs`、macOS `~/Library/Logs`）；iGPU 开关在非 Windows 上说明「不适用」而不是报错 |
| 精度文件名 | 四个地方各写一遍 `encoder.int8.onnx` | `voice_loop/tts/precision.py` 一份，`scripts/test_precision.py` 守着 |

没做、也不该假装做了的：字幕在非 Windows 上**不会点穿**（拿不到 `WS_EX_TRANSPARENT`，
也拿不到工作区矩形，位置按屏幕高度估算），Wayland 下截屏可能全黑，
`[vision] file_roots` 的中文目录名在非中文系统上要改成实际路径（`vision.py` 里已有
`桌面→Desktop` 这类别名表，英文系统直接可用）。

### 16.4 可部署性自检：`scripts/check_deploy.py`

只读、几秒跑完、每项都带「怎么办」，分七类：

| 类别 | 查什么 | 为什么它在搬家时会坏 |
|---|---|---|
| 1 环境 | OS / Python 版本 / **项目路径带空格或非 ASCII** / 控制台编码 | 原生库（onnxruntime、espeak-ng）偶发加载失败；`settings.py` 用 `tomllib`，Python 必须 ≥3.11 |
| 2 依赖 | 13 个包分「必需 / 某后端才要 / 纯附加」三档 | 缺 pip 名和命令直接列出来，不用猜 |
| 3 配置 | `config.toml` 里每个路径是否存在、是否写了绝对路径 | **绝对路径换机器必失效**；模型路径缺失可以直接指到 `download_models.py` |
| 4 模型 | 体积下限 + 每个角色目录里有哪些 onnx | 「下了一半」的文件比缺文件更难查 |
| 5 服务 | Ollama 可达 + 模型是否拉过；麦克风/扬声器能否枚举 | 这两样是「程序能跑但用不了」的最常见原因 |
| 6 平台能力 | 关屏 / 字幕点穿 / 后台服务 / iGPU 开关 / 剪贴板，逐项说当前系统会怎样 | 换系统后功能会静默降级，先说清楚 |
| 7 磁盘 | 三个目录可写 + 可用空间（模型 + checkpoint 动辄几个 GB） | 微调一个角色要留 1.9 GB × 保留数 |

> ★踩的坑★：**OpenVINO 模型的体积要看 `.bin`，不是 `.xml`**。
> `.xml` 只是计算图（Whisper encoder 的 `.xml` 才 1.4 MB，权重 645 MB 全在 `.bin` 里），
> 拿 `.xml` 去比 100 MB 的门槛，会把一份好好的模型判成「像是没下完」。
> 凡是「按体积判完整性」的检查，先确认**哪个文件才是主体**。

### 16.5 NPU（Intel AI Boost）实测：硬件在，但没用武之地

起因：用户在 Windows 资源监视器里看到 NPU，问「有用吗」。以前这里只有一条模糊的记忆
（「Whisper 在 NPU 上会崩进程」），所以重新量了一遍——`scripts/probe_npu.py`，
每段跑在独立子进程里（NPU 编译失败是硬崩，同进程里试会把探测脚本一起带走）。

| 同一台机器、同一份模型 | CPU | Arc 核显 | NPU |
|---|---|---|---|
| Silero VAD（512 采样点，热态） | **0.4 ms** | — | 3.8 ms（**慢 ~9 倍**） |
| Whisper encoder，静态 `[1,128,3000]`（30 秒音频） | 3.4 s | **0.168 s** | 1.33 s（**慢 7.9 倍**） |
| 同上，编译耗时 | 2.1 s | 6.2 s | **294 s** |
| Whisper encoder，动态 `[?,128,3000]`（= 日常用法） | √ | √ | ✗ 编译失败 |

失败信息是 Level0 的 `ZE_RESULT_ERROR_INVALID_ARGUMENT`（早先那次更狠：`0xC0000005` 硬崩，
vpux-compiler 报 `Channels count … != 128`）——**同一个原因**：NPU 要静态 shape。

三条结论，从强到弱：

1. **就算为它改造导出也不值得**：得把每句话都 pad 到固定长度（比如 30 秒），短句白算；
   而且改完还是比核显慢 8 倍，还得额外背着 294 秒的编译（要开 OpenVINO 的模型缓存）。
2. **小模型上它反而更慢**：VAD 这种 0.4ms 的活儿，NPU 的固定开销比计算量还大（3.8ms）。
   也就是说「待机时把 VAD 放 NPU 省电」这个想法在本机不成立。
3. **链路根本接不上**：`sherpa-onnx`（SenseVoice / ZipVoice / Piper）用的是它自带的
   onnxruntime，只有 `CPUExecutionProvider` 与 `AzureExecutionProvider`，**换不了 EP**；
   Ollama 没有 Intel NPU 后端。所以真能碰 NPU 的只有 whisper 那条 OpenVINO 路径，
   而那条路已经被核显占了（0.168s，比 NPU 快 8 倍）。

> 唯一留下一个「将来可能成立」的场景：**核显被 Ollama 占满时**（qwen3.5:4b 就跑在
> Arc 上），把 ASR 挪到 NPU 可以避开争用。但按上表的差距，先用
> `[asr] whisper_device = "auto"` 的回退就够，没必要现在动。

### 16.6 这一轮的方法论教训

1. **归因要用只改一个变量的对照实验闭环**——这一轮最大的收获来自「fp32 只差 6%」这一行，
   而不是任何推理。没有对照，归因就只是猜想（15.5 已经写过一次，这次是加强版）。
2. **「报告说缺、实际能跑」这类自相矛盾，一定是判断逻辑写了两份**：精度文件名原先在
   四个地方各写一遍，于是「查文件全不全」和「真正加载哪个文件」随时会分叉。
   现在收成一个 `precision.py`，并在离线测试里断言「除它以外没有第二份」。
3. **换平台/搬机器这类改动，要有办法一次问清楚**：`check_deploy.py` 就是把
   「环境、依赖、路径、模型、服务、平台降级、磁盘」这七个问题固定下来，
   省得每次靠现场回忆踩过哪些坑。

### 16.7 沙沙声的真正来源：素材底噪与参考音频（2026-09-24 下午）

> ⚠️ **2026-09-25 更正：本节的核心结论是「指标假象」，别照它去处理素材。** ⚠️
> 本节用的「安静帧高频占比」= 能量最低 25% 的帧里的 >6 kHz 占比。后来逐帧看了阿米娅
> `交谈1.wav`：那些帧的 RMS 只有 **−78.8 dBFS**（数字静音附近的抖动/转换器底噪），
> 而 25~50% 那批帧是 **−37.6 dBFS（真停顿）HF 只有 3.2%**、语音本体 **1.1%**。
> 也就是说 82% 那个数字量的是**耳朵听不到的东西**。
> 换用「安静帧相对语音 −45~−15 dB」的口径后，两条参考的安静帧高频是
> **凯尔希 0.37% / 阿米娅 1.06%**——都干净，谁也不比谁脏 4.5 倍。
> 而且把参考当真去净化（谱门/高架）在 5 遍配对里**反而让输出更亮**（见 18.2）。
> 结论：**沙沙声不在参考音频里**；`pick_voice_ref.py` 的安静帧口径要按这个教训改成
> 相对电平 + 排除数字零（已在 `ab_clone_model.py` 里改好，见 18.1）。
> 下面这一节保留原文，只当「当时的推导过程」看。

16.1 写完「量化有影响但不是主因」之后，A/B 网格跑完了（40 个 wav），于是把整张表
当数据看了一遍——**先量化噪声，再看差异**。结论比预期干净，而且又推翻了 16.1 的第 3 条。

#### ① 单点指标根本不可信（噪声能到 3 倍）
同一模型、同一精度，只把采样步数从 4 换成 8/16/32（= 换四次随机采样）：

| 配置 | 4 步 | 8 步 | 16 步 | 32 步 | 极差 |
|---|---|---|---|---|---|
| 凯尔希 出厂蒸馏·短句 | 3.89% | 9.63% | 13.61% | 4.89% | **3.5 倍** |
| 凯尔希 微调·短句 | 5.71% | 8.73% | 10.37% | 9.62% | 1.8 倍 |
| 阿米娅 微调·短句 | 11.28% | 4.87% | 3.94% | 5.98% | 2.9 倍 |
| 凯尔希 微调·长句 | 11.08% | 8.85% | 8.37% | 9.87% | 1.3 倍 |

两件事：**短句那一格是噪声重灾区**（整条音频才 0.7~1 秒，一两个字的齿音就能主导指标）；
**步数并没有稳定降噪**（非单调）——「加步数治沙沙声」这个假设被否掉了，
代价那边更不用谈（fp32 32 步：合成 7 秒音频要 127 秒）。
唯一可信的比法是**同一步数下配对**（`python scripts/ab_clone_model.py --summary <csv>`）：

| 组 | fp32 更低的档数 | 平均差 | 结论 |
|---|---|---|---|
| 凯尔希·长句 | **4/4** | −2.63 个百分点（SEM 0.19） | 方向一致 |
| 阿米娅·短句 | **4/4** | −2.05（SEM 0.78） | 方向一致 |
| 阿米娅·长句 | 2/4 | −3.58（SEM 4.02） | 不可区分 |
| 凯尔希·短句 | 3/4 | −0.38（SEM 2.19） | 不可区分 |

#### ② 最大的差异在**角色之间**，而且量出来在**素材**上

| 38 条素材 | 整条高频占比（中位） | **安静帧高频占比（中位）** |
|---|---|---|
| 凯尔希 | 3.73% | **7.54%** |
| 阿米娅 | 12.35% | **34.36%** |

「安静帧高频占比」= 只取能量最低的 25% 帧（停顿 / 塞音成阻 / 气口）再算 >6 kHz 占比。
**为什么必须换成这个指标**：整条指标受**文本**影响（「是/四/十/s/x」多的句子天然偏高），
而安静帧里只剩底噪与气声，与句子无关。两边被选中的安静帧占比一样（24.3% vs 25.3%），
所以是同一把尺子 → **阿米娅的素材底噪就是凯尔希的 4.5 倍**。
文件格式已排除：两边都是 44100 Hz / 单声道 / PCM_16。

#### ③ 是「模型毛」还是「参考毛」：2×2 交叉

两个角色是**同时**换了模型和参考（阿米娅换了模型+参考，凯尔希也换），所以做了一次交叉
（`python scripts/pick_voice_ref.py --cross kaltsit amiya`，长句 / 4 步 / int8）：

| 整条高频占比 | 参考=凯尔希 | 参考=阿米娅 |
|---|---|---|
| 模型=凯尔希 | 9.55% | **23.52%** |
| 模型=阿米娅 | 15.21% | 26.82% |

- 同参考换模型：×1.6 / ×1.1
- **同模型换参考：×2.5 / ×1.8** ← 更大

→ **推理时那条参考音频是噪声的「载体」**：参考自己只差 1.4 倍（整条口径），到输出里被放大成 2.5 倍。
两个模型的放大倍数差不多，只是阿米娅的模型带一个更高基线（约 +13 个百分点）——
那个基线来自她自己的素材（②已经证明素材脏）。

#### ④ 于是「该修哪个」的顺序也换了

| 手段 | 效果 | 代价 | 结论 |
|---|---|---|---|
| **换 / 处理参考音频** | 输出高频 ×1.8~2.5 | 零（改一行配置） | **先做这个** |
| 换素材重训 | 能压低基线 | 几十分钟训练 + 得先有好素材 | 素材脏才值得 |
| 换精度 int8 → fp32 | −2~3 个百分点 | 合成时间 ×2 | 最后考虑 |
| 加步数 | **没有可测效果** | ×4~×30 | 不做 |

候选参考（`python scripts/pick_voice_ref.py --who <角色>` 会列全表）：

| 角色 | 现在在用 | 安静帧高频 | 最干净的候选（3.5~8 秒内） | 安静帧高频 |
|---|---|---|---|---|
| 凯尔希 | 干员报到 7.79s | 6.83% | **完成高难行动 3.68s** | 4.01% |
| 阿米娅 | 交谈1 8.02s | 不在前六 | **完成高难行动 6.60s** | 8.17% |

★仍然是「先听后改」★：这些数字只能筛掉明显毛的，定不了好不好听；
而且换参考会同时改变语速与韵律（见 15.1 ②）。

#### ⑤ 方法论（第 16.6 节的加强版）

1. **先量噪声，再谈差异**：把「步数轴」当重复测量，才发现前面的单点对比全是假的。
   凡是「改一个参数、看一个数字」的实验，先让同一配置多测几次，把噪声水平拿到手。
2. **留意指标会不会被别的东西污染**：整条高频占比被「这句话有多少齿音」污染 →
   换成安静帧指标后，4.5 倍的差异一眼就看出来了。
3. **全因子交叉比单因子实验便宜**：2×2 只跑 4 次合成，就分清了「模型 / 参考」谁的锅；
   而之前两轮都在拿单变量猜。
4. **同一个数字，先问它在不同口径下是否一致**：`完成高难行动` 在凯尔希那里整条只有 4.06%
   （第二干净），安静帧口径也是第一（4.01%）；而 `精英化晋升2` 整条 3.12% 更漂亮，
   安静帧却 9.63% —— 两个口径不一致时，**安静帧那个更可信**（它没被文本污染）。

## 17. 事件统一与事件链（已完成）

用户的判断是对的：**闹钟和日程本质都是「事件」，只是属性不同**。
原来分成两份文件、两套字段、两套处理器，代价不是「看着不优雅」，而是实打实的 bug 温床：

* `_handle_alarm` 里要写 **3 条让位规则**（带周期 / 多个提前量 / 是件正经事）把话让给
  `_handle_schedule`，而它们中间的每条缝都漏过东西：「取消今晚十点的闹钟」凭空多出一条、
  「下周三下午 3 点有社团活动」日程里什么都没有（详见 15 节）；
* 模型要在 7 个工具里挑（`add_alarm` vs `add_schedule`），挑错就**静默丢东西**；
* 「我这周有什么安排」看不到闹钟，因为两边根本不是一张表。

### 17.1 统一后的模型：闹钟 = 提前量 0 的事件

`voice_loop/events.py`（新）取代两种存储。关键一步是**别再造新词**——
新 schema 就是旧 schedule 的超集，闹钟退化成它的一个特例：

```jsonc
{
  "id": 1,
  "kind": "reminder",              // reminder（叫一声）| event（要占时间的事）
  "title": "喝水",                  // 旧闹钟叫 what，现在统一叫 title
  "category": "meeting",           // 可选：course/meeting/task（旧 schedule 的 kind）
  "start": "2026-09-21 10:05:30",  // 旧闹钟叫 when；★保留秒★，「十分钟后」靠它
  "repeat": "weekly",              // 缺省 = once（= 闹钟）
  "weekday": 2, "time": "09:00",   // 重复用
  "duration_minutes": 0, "location": "", "note": "", "until": "",
  "remind_before": [0],            // ★闹钟就是 [0]★；日程可以是 [1440, 30, 0]
  "chain": {"after": 3, "on": "done", "then": "notify"},
  "state": {"fired": [], "done": [], "skipped": []}
}
```

| 原来的名词 | 现在是什么 |
|---|---|
| 闹钟 | `kind=reminder` + 没有 `repeat` + `remind_before=[0]` |
| 日程（一次性） | `kind=event` + `start` |
| 日程（每周课） | `kind=event` + `repeat=weekly` + `weekday`/`time` |
| 「提前一天和半小时提醒我」 | `remind_before=[1440, 30]`（闹钟是它的退化情形） |
| 跳过一次（「下周三不上课」） | `state.skipped` 里那一天 |
| 已经播报过 | `state.fired` 里的 `"发生时间\|提前量"` |

### 17.2 三种状态为什么必须分开记

    state.fired    已播报过的「(发生时间|提前量)」——二维去重，最多留 40 条
    state.done     已完成的「发生时间」——★事件链就靠它★
    state.skipped  被单独跳过的「日期」

混成一个布尔就会出现「今天的课完成过 → 下周的课不再提醒」这类 bug。
原来的两套各只用了其中一半（闹钟一个一维 `fired`、日程一个二维 `_fired` 加一个 `skip`）。

### 17.3 到期引擎：一条路径，两处**故意**的差异

```python
due(items, now, default_lead, blocked)   # 会就地写回 state.fired
```

两种事件共用「(发生时间, 提前量) 到点了没播过」这一条判断，只有两处策略不同：

| 差异 | 闹钟 | 日程 | 为什么 |
|---|---|---|---|
| 错过之后 | **没有回看上限**：关机一整天回来仍然补报 | 「到点」那次只在 **5 分钟**内算数 | 闹钟是「我现在要你提醒我」；三天前那节课的「开始了」再播一遍毫无意义 |
| 回看窗口 | 一次性：直接看锚点 | 按最大提前量往前找 | 提前 30 分钟的提醒必须在**开始之前**发出来——只盯已经过去的时刻是永远发不出来的（这个坑我第一版就踩了，测试抓住了） |

★这里还有一条实测教训★：`due()` 看的时间窗必须是 `now + 最大提前量`。
第一版写成只看 `now`，于是所有「提前提醒」全都不响，而「到点提醒」正常——
测试里那条 `跟导师见面（提前 10 分钟）` 直接把问题指出来了。

### 17.4 事件链（语义已与用户确认）

```jsonc
"chain": {"after": 3, "on": "done", "then": "notify"}
```

* `after`：上游事件的 `id`（迁移时已把两份文件的 id 重排，不会再撞）；
* `on`：上游达到什么状态算「发生」——`done`（做完了，默认）/ `start`（开始了）；
* `then`：那时做什么——**只实现 `notify`（解锁下游的提醒）**，
  不是「把 B 也标记成做完」。

**两条关键语义是问过用户才往下写的**（做错了就是白写）：

| 问题 | 选定 | 后果 |
|---|---|---|
| 「完成 B」是什么意思 | **解锁 B 的提醒** | 不需要新增「把 B 标完成」的动作 |
| A 何时算完成 | **到 A 的结束时间自动算** | ★**不需要语音入口说「做完了」**★——完成判定是**纯时间推导**的 |

于是整个链是**纯函数式的、不写任何状态**：

```python
chain_blocked(item, start, all_items, now)
#  不解锁的条件：上游还没发生过；或上游那次「结束时刻」（on=done）/「开始时刻」（on=start）还没到
#  手动 mark_done() 可以在结束前提前解锁（可选覆盖，不是必要条件）
```

设计上的四个细节，每个都是为了避一个坑：

1. **按「每一次发生」判定**：重复的链（「每周三组会结束后提醒我写周报」）要求
   **每个** B 之前有一次已结束的 A——不能「第一次解锁后永远解锁」（测试里专门盯着 9-23 和 9-30 两周）。
2. **只挡「自动播报」，不挡「看得见」**：被链挡住的日程仍然会出现在「这周有什么安排」里，
   否则用户会以为链上的事丢了——实测「查不到」比误报更难排查。
3. **上游被删掉就自动解挡**，免得下游永远不响（链最容易埋的一个死锁）。
4. **没有时长的 A = 开始即结束**，所以那种情况下 `on: done` 与 `on: start` 等价
   （`end_of()` 里写明了这一点，免得以后有人以为算错了）。

因为不写状态，所以**改上游时间、删上游、改 `duration_minutes` 都会立刻反映到下游**——
没有「一次算出结果就冻结」的陈旧状态。代价是每次 `due()` 要多算几次上游的发生时间
（拿 `occurrences()` 往前找一个，最多 8 个候选，实测可忽略）。

### 17.6 兼容窗口

`skills.alarms` / `skills.schedule` 现在挂在 `EventStore.view(kind)` 上，而它是
**只按 kind 过滤、不改字段名**的视图（不是「翻译旧字段」的适配层）——
因为统一后的 schema 本来就用旧日程那套名字（`title`/`start`/`repeat`/`remind_before`），
真正改名的只有闹钟那三个：`when→start`、`what→title`、`fired→state.fired`。

三条规矩（都有测试守着）：

1. `load()` 返回**库里的原对象**而不是副本——旧代码有「就地改字段再 save」的写法，
   返回副本会把改动静默丢掉；
2. `save(items)` 只替换**这一类**，另一类原样保留（否则闹钟一保存就把日程洗掉）；
3. `update` / `remove_at` 的下标是「**这一类里的第几个**」，与旧代码语义一致。

这么设计是为了让重构**行为等价**：既有的 170 多处断言不用重写，
它们验的是「闹钟和日程**各自的**行为」，正好可以当这次改造的安全网。

### 17.7 文本层：闹钟也能重复（起因是用户的一句话）

这句话正好戳在旧设计最别扭的地方。旧 `_handle_alarm` 有三条**让位规则**，
碰到就把请求转给日程处理：

1. 说了重复周期（`parse_repeat` 有结果）；
2. 说了多个提前量；
3. 说了日期+钟点，而且带了事件名词。

于是「每个工作日八点半叫我起床」被规则 1 踢到日程那边，而日程只认
「每周X / 每N天」——**根本没有「工作日」这个概念**，最后的落点是：一条不会重复的闹钟。
用户要的功能，是被架构挡住的。

新的分界（`event_text.classify()`，全文唯一一处）：

    kind 不由「有没有重复」决定，而是由「是不是一件占时间的事」决定：
      有事件名词（课/会议/约/活动/考试…）、有地点、有时长、有「A 点到 B 点」 → event
      只说「提醒我 / 叫我 / 喊我」                                          → reminder

两者都能重复、都能有多个提前量、都能带地点/时长/截止日期；`kind` 只决定两件事：

| | 默认提前量 | 播报口径 |
|---|---|---|
| `reminder` | `[0]`（到点） | 「时间到了，起床。」 |
| `event` | `[10]`（默认提前 10 分钟） | 「提醒你：十分钟后，也就是10:00，有组会，地点…。」 |

这样「闹钟」和「日程」的差别就只剩**说话方式**了，而「工作日闹钟」自然成立：
`kind=reminder` + `repeat=weekdays` + `time=08:30`。

为了让这句话真的能听懂，三处配套改动：

1. `nlp_time.parse_repeat` 新增 `weekdays`（工作日/周一到周五）；`每天` 从
   `interval+every_days=1` 改成 `daily`——★**固定钟点，不是「上次结束的 24 小时后」**★，
   后者会漂（前一天晚睡，整条链整体后移）。裸「每周」（没写星期几）也补上了。
2. `events.occurrences()` 支持 `daily` / `weekdays`，周末跳过，并遵守 `until` / `state.skipped`。
3. 新模块 `voice_loop/event_text.py`：**文本侧唯一的家**
   —— 抽取（`extract()`）、分类（`classify()`）、落库（`to_item()`）、播报（`render_fire()` /
   `render_added()`），并把原先散落在 `skills.py` 里的清洗正则（时间词、提前量、填充词、
   地点、标题归一化）收拢过来。

#### 两个坑（都有测试守着）

* ★**原因从句必须剥掉**★。用户那句里有两个钟点（9 点有课、8 点半闹钟），
  不剥的话 `parse_datetime` 很可能取到「九点」——闹钟就定错了。
  `split_reason()` 按「那就/所以/因此…」切开，只用要求那半句取时间；
  而原因那半句还有用：标题空着时拿它兜底（「有课」→ 优先词表 → 「上课」）。
* ★**提前量不是时长**★。「每周三九点上课，提前半小时」里的「半小时」属于
  `remind_before`，当成 `duration_minutes` 会让条目凭空长出一条 30 分钟的尾巴。
  抽取时长前先用 `LEAD_WORDS` 把提前量说法摘掉。

顺手修掉的一个小毛病：认不出类别时**不要猜成 `task`**（猜错会让「有哪些课」查不到），
留空比猜错好。

### 17.8 连 `kind` 也去掉：只有一张可填可不填的表

17.7 把「闹钟 vs 日程」从**让位规则**换成了**一条分界规则**，但分界还得靠一个 `kind`
字段存起来。用户接着指出：连这个区分都不需要——

> 闹钟的关键在于准时响起，日程可以需要提前提醒；二者其实没有更本质的区别，
> 而且闹钟应该支持无事件，纯闹钟；或者说更本质的，我们并不需要区分闹钟和日程，
> 应该更加模块化，如果说了持续时间，重复规则等就加上，没有就默认为0；
> 只是在删除或更改带有重复的事件时需要确认。

他是对的：`kind` 只是「用户说没说过某些字段」这个事实的**缓存**，而缓存会跟事实不一致
（迁移、改时间、加提前量都可能让它失真）。删掉之后，模型变成一张表：

| 字段 | 缺省 | 说了什么才加上 |
|---|---|---|
| `title` | 空（**纯闹钟**：只负责准时响） | 「提醒我吃药」→ 吃药 |
| `remind_before` | `[0]`（准时） | 「提前半小时」→ `[30, 0]` |
| `repeat` + `weekday`/`day`/`every_*` | 无（一次） | 「每周三／工作日／每天」 |
| `duration_minutes` | `0` | 「三点到四点半」→ 90 |
| `location` / `note` / `until` | 空 | 「地点…」「备注…」「到…为止」 |

连带的三处简化：

1. **没有 `kind` 可读了**，所以 `due()` 里那两处**故意的**策略差异必须换个判据——
   改成按「一次性 / 重复」分，语义反而更清楚：
   * **一次性**（没有重复规则）：`lead=0` 那次**无回看上限**——就是「准时响起」的兜底，
     关机、服务没停时错过的，回来仍然要响；
   * **重复**：`lead=0` 只在 :data:`LEAD_GRACE`（5 分钟）内算数——三天前那节课的
     「开始了」现在再播一遍没有意义，而下一次很快就到。
2. **`KindView` / `view(kind)` / `reminders()` / `schedules()` 全部删除**——
   兼容窗口到此结束（这正是它的用途：让 17.7 之前的那步不必同时改 173 处断言）。
3. **播报不再按类型分口径，改按提前量分**：
   * 准时 → 「时间到了，吃药。」／「时间到了，开组会，地点教学楼 A302。」
   * 提前 → 「提醒你：十分钟后，也就是10:00，开组会，地点教学楼 A302。」
   原来那句「有…」的措辞也去掉了：「有吃药」不通，而「…，吃药。」两种都通。

另外按用户要求补上 **`needs_confirm(item)`**：带重复的事件删改前必须先问一句
（影响的是往后所有次），纯闹钟直接做。这是在**数据层**给出判据，
`skills` 那边的确认流程在下一步（处理器合并）落地。

★纯闹钟★的连带有：`title_of()` / `display_title()`（空标题显示成「闹钟」）、
`new_event()` 的 `title` 变成可选、迁移时 `what` 缺失不再硬塞「提醒」。

## 18. 音质第二轮：沙沙声与语气连贯（2026-09-25）

起因：用户说「继续优化音频模型，要去掉沙沙声和保留语气连贯」。这一轮**先量，再动**，
结果推翻了 16.7 的根因，并把「能做的」收成四个旋钮（已进 `config.toml`）。

### 18.1 先纠正三件事（全是量出来的，不是推理）

1. **★模型不是确定性的★**。同一个参考、同一句话、同一个配置，连跑三次：

   | 遍 | 输出时长 | 整条高频 |
   |---|---|---|
   | 1 | 6.85 s | 8.22% |
   | 2 | 6.41 s | 4.63% |
   | 3 | 6.61 s | 8.63% |

   —— 旧笔记里「同配置跑 4 次输出时长极差 0.00s（完全确定性）」是**错的**，别再当依据。
   后果：**任何单点对比都能把噪声当效果**（这一轮我自己也差点被绕进去：
   同一个「参考谱门」配置，三次整条高频 10.79 / 56.37 / 20.44%）。
   规矩：**配对 + 多遍 + 看符号一致性**，不看单次中位数。

2. **★16.7 的「安静帧高频」量的是听不见的东西★**。逐帧看阿米娅 `交谈1.wav`：
   最低 25% 的帧 RMS **−78.8 dBFS**（数字静音附近的抖动）HF 92%；真停顿那批
   （−37.6 dBFS）HF 只有 **3.2%**；语音本体 **1.1%**。
   新口径（`ab_clone_model.py`）改成**相对语音电平 −45~−15 dB 且排除数字零**，
   两条参考的安静帧高频是 **凯尔希 0.37% / 阿米娅 1.06%** → 都干净。
   （顺手修掉一个真 bug：`frame_db` 把 int16 当浮点算，电平整体偏 +90 dB，
   于是「可闻安静帧」永远是空的、底噪报出 12.6 dBFS 这种不可能的值。）

3. **沙沙声住在模型侧，不在参考里**：「凯尔希模型 × 阿米娅参考」这种交叉里，
   同参考换模型的差别远大于同模型换参考（新口径下也不再是 16.7 的 ×2.5）。

### 18.2 参考音频净化：做了、量了、**没用**（默认 off）

新增 `voice_loop/tts/refclean.py`：从参考自己的安静帧估噪声底 → 软谱门（只动幅度、
不改时长，STFT→ISTFT 精确重建）+ 可选高架 + 响度归一；`[tts] ref_clean` 三档。

5 遍配对（同一遍里对比「原样」）：

| 变体 | 凯尔希 整条高频 | 阿米娅 整条高频 |
|---|---|---|
| 原样 | 10.9（8.2~15.4） | 30.4（30.3~36.9） |
| 参考谱门 | **20.4**（10.8~56.4）↑ | 27.7（23.4~29.1） |
| 参考谱门 + 高架 −3 dB | **23.5**（8.2~35.2）↑↑ | 20.5（16.9~30.5） |

方向不一致、量还在噪声里 → **不做**（`ref_clean = "off"`），模块与开关留着给以后
（比如换一批更脏的素材时）。留下的副产物是 `data/ref_cache/`：开着它就能听
「模型到底听到了什么」。

### 18.3 输出去嘶声：**唯一 5/5 一致有效的旋钮**（已默认 −3 dB@7 kHz）

在输出侧加一个高架（`[tts] out_tilt_hz / out_tilt_db`，dsp 只花几毫秒/块）：

| | 阿米娅 | 凯尔希 |
|---|---|---|
| 原样（中位，5 遍） | **31.7**（25.9~40.1） | **11.9**（8.6~13.1） |
| −3 dB @ 7 kHz | 21.3（13.2~26.0）　**5/5 变干净** | 6.7（6.2~36.0）　4/5 |
| −6 dB @ 6 kHz | **11.1**（9.5~12.1）　**5/5** | 2.8（2.1~3.3）　**5/5** |

两条附带好处：**每遍之间的差别也变小了**（阿米娅 −6 dB 那档 5 遍落在 9.5~12.1%，
原样是 25.9~40.1%）——听着就是「每次都是同一个人、同一个亮度」。
代价：齿音也会被一起削，**这一项必须耳朵定**（试听 `sessions/voice_ab2/tilt_*.wav`，
默认取保守的 −3 dB@7 kHz）。

### 18.4 语气连贯：三个「不碰语音、只动静音/电平」的旋钮

1. **★按比例压长停顿★（`trim_shrink_pause = 0.35`）**。实测模型在逗号处能停
   **0.85~1.31 秒**（人类 0.2~0.3 秒）——听着就是「说到一半卡住」。
   平压到 260 ms 干净，但会把逗号和句号压成一样长（**语气对比没了**）；
   比例压只吃掉超出部分的 65%：

   | | 停顿序列 | 总时长 |
   |---|---|---|
   | 原样 | 1310 / 940 / 740 / 300 ms | 5.79 s |
   | 平压 450→260 | 260 / 260 / 260 / 300 ms（全一样） | 3.58 s |
   | **比例压 0.35** | **620 / 490 / 420 / 290 ms** | 4.35 s |

   ★字/有声秒完全不变★（8.21 字/秒，压前后一样）——它只动静音，不碰发音。

2. **块间电平对齐（`chunk_level_db = 1.5`）**：ZipVoice 采样生成，一句大一句小。
   实测每块有声电平极差 **凯尔希 2.7 dB / 阿米娅 3.2 dB** → 对齐后 **1.2 / 1.7 dB**。
   上限 1.5 dB 是安全绳：只修明显的忽大忽小，不把语气里的轻重压平。

3. **按标点的接缝补白（`join_pause_comma_ms = 160` / `join_pause_period_ms = 320`）**：
   一句话被 SpeechChunker 切成多块时，块与块之间原来只补 `sentence_silence`（80 ms）——
   句号后面只停 80 ms 听着是「两句黏在一起」。现在逗号 160 / 句号 320。

## 19. 「语气连贯」的真身：音区（音高 F0）守卫（2026-09-25 第二轮）

起因：用户澄清了一句关键的话——「我说的语气连贯是**不要出现异常的高亢和低沉**」。
第 18 节那三个旋钮全在动**停顿和电平**，一个都没碰到音高。这一节补上，并且**先把尺子修好**。

### 19.1 先把尺子修好（这一节最重要，代价也最大）

音高测量是这一轮最大的坑，先后踩了四个：

1. **第一版跟踪器（归一化自相关 + 谐波性打分 + 倒谱交叉校验）在真人参考音上就露馅**：
   0.25 s 一格的中位 F0 在 150/280 Hz（差一个八度）之间来回翻；连 Piper 那种
   「稳定得不能再稳定」的合成音也被量出 159~281 Hz 的摆动。**那是尺子病，不是声音病。**
   自相关有 1/f 偏差，容易锁到二次/三次谐波或共振峰上。→ 换成 **YIN**
   （累积均值归一化差函数 d'(τ)，取**第一个**低于阈值 0.15 的谷 + 抛物线插值）。
2. **候选基频的搜索窗太窄**：±3% 在 130 Hz 处只有 ±3.9 Hz，而 24 kHz / 960 点 FFT
   的频点间隔是 12.5 Hz → 窗口里一个频点都没有 → 真基频被判「没能量」→ 锁到二次谐波。
   → 窗口改成 `max(f*3%, 一个频点宽)`。
3. **拿「谱心 >1800 Hz = 擦音」当清音门槛是错的**：实测凯尔希浊音帧的谱心中位就有
   **2735 Hz**，这一条会把 **64%** 的真浊音帧一起挡掉（统计全偏，还看不出来）。
   → 删掉谱心门槛，改用 YIN 自己的差函数谷 + 谐波性打分。
4. **中位滤波不要填 NaN**：拿邻近音高去填清音帧等于凭空造「有声」（有声率虚高、停顿变短）。
   现在只对有声帧做中位滤波，NaN 保持 NaN。

验证方法留下来（以后改任何指标都先跑这两条）：

* **已知答案的合成信号**（`scripts/test_pitch.py`）：对数滑音（误差 ≤0.22 半音）、
  二次谐波陷阱（0.10×130Hz + 0.30×260Hz **必须**回到 130Hz）、弱基频（0.08×90Hz → 90Hz）、
  擦音/静音（有声率 0%）、22.05/24/44.1 kHz 同答案、句内插静音**不改**中位音高；
* **Piper 当对照组**（干净、无背景、音高极稳）：逐帧轨迹必须平滑——实测相邻帧跳变
  中位 0.15 半音、p99 1.0 半音、最大 2.5 半音。

★结论规矩★：**换尺子之前不要下结论**。这一轮前半段那些「模型忽高忽低」的数字里，
有相当一部分是尺子错，不能当依据。

### 19.2 量出来的事实（同模型、同参考、同一句话各 6 遍）

| | 每遍 F0 中位 | 中位极差 | 单遍离群帧 | p99 偏离 | 单遍耗时 |
|---|---|---|---|---|---|
| 凯尔希（参考自己 180 Hz） | 176 / 183 / 183 / 182 / 185 / 195 Hz | **1.74 半音** | 0~7.1% | 5.0~11.1 半音 | 7.9 s |
| 阿米娅（参考自己 258 Hz） | 252 / 252 / 260 / 262 / 274 / 290 Hz | **2.40 半音** | 1.5~3.2% | 6.2~8.6 半音 | 8.4 s |

读法：**整句音区在飘**（阿米娅最远偏 +2.0 半音 = 一个全音，凯尔希 +1.4），
而**句内摆幅是正常的**——合成 IQR（凯尔希 4.4 / 阿米娅 3.3 半音）跟各自的真人参考
（4.3 / 2.5 半音）基本一样，p99 偏离也和参考同档（参考 5.8 / 6.9 半音）。
所以「异常的高亢/低沉」不是「模型比人更夸张」，而是**这一遍整体抽到了另一个音区**：
一问一答里上一句正常、下一句整句拔高，耳朵一听就听出来。

两条附带事实：
* **42 字的长句也只产出 1 块**（实测 8.99 s 一块）→ 音区判定不需要额外攒延迟
  （量一次的代价：6 秒音频 87 ms、10 秒 125 ms = 一次合成时间的 1~2%）；
* **`clone_guidance` 不是解**：1.5 时极差 1.91 半音但整体音区被抬高约 1.5 半音；
  2.5 时极差反而涨到 **4.58 半音**（更差）。默认保持不动。

### 19.3 做法：重采守卫（★不碰变调 DSP★）

合成完先用同一把尺子量整句音区，跟**参考音频自己的音区**比（靶子 = 参考音的中位 F0，
引擎启动时量一次并打印）；偏离超过 `pitch_guard_st`（默认 **1.5 半音**）就
**丢掉重采**，最多 `pitch_guard_tries`（默认 2）遍，然后无论好坏都用最后一遍出声。

* **为什么不直接变调**：变调 DSP 会毁共振峰/音色（第 18.4 节已经吃过「改时长 → 声不对词」的亏）。
  这里是「采样抽到了另一个音区」，重采就是同一分布下重新抽一次，不引入任何失真。
* 实现要点（`voice_loop/tts/zipvoice_tts.py`）：先量**第一块**再决定出不出声；
  被丢掉的那一遍要**抽干**（同一个引擎上并发跑两次不保险）；`f0_median` 量不出来
  （静音/擦音/有声帧太少）→ 返回 `None` → **不裁**（宁可放过一遍，也不能因为量错白等一遍）。
* 代价：触发的那句多花一遍合成时间。实测 6 遍里阿米娅 1 遍触发（阈值 1.5）、凯尔希 0 遍；
  `pitch_guard_st = 0` 可整体关掉。

### 19.4 验证

* `scripts/test_pitch.py`：**37 条离线断言**全绿（滑音/陷阱/弱基频/擦音/静音/采样率/量纲/
  停顿不改音高/register_st 精度/守卫判定真值表/中位滤波保持 NaN）。
* 端到端（故意把阈值压到 0.05 逼它触发）：
  ```
  [tts] 这一遍整句音区偏了 -0.1 半音（靶子 259Hz），重采第 2 遍…
  [tts] 音区还是偏 +1.7 半音（重采到上限了），先用这一遍出声
  ```
  音频照常出（6.69 s，2 块），耗时 40.7 s（≈两遍；阈值 1.5 那遍没触发，20.0 s）。
  ★注意重采不保证变好★（这是采样），它只保证「明显偏了就再抽一次」。
* 新工具 `scripts/pitch_report.py`：拿 `--ref` 当靶子，列出每条 wav 的
  音区 / 摆幅 / 离群 / 持续偏离 / 跳变 / vs靶子，并标出「会被重采」的那几条。

### 19.5 上车三句话

1. 听出「突然高/低」就看**音区（F0 中位）**这一列；「句内起伏大不大」看**摆幅**列——
   后者要跟参考音比才有意义，别直接改参数。
2. 定音区的只有两个来源：**参考音频**（换参考能整体挪 ±5 半音）和**采样**（同参考同文本
   ±2.4 半音，守卫治的就是它）。
3. 改任何 DSP/指标之前：先跑合成自检，再拿 Piper 当对照组；**别用一把没验过的尺子下结论**。

### 19.6 「要不要加数据重训？」——量了，不用（2026-09-25 追加）

用户的疑问是「是不是我给的参考/数据量不够，需要更多数据训练」。用两个实验回答（同一句话、
守卫关掉、各自以参考音频自己的音区为靶子）：

**(1) 训练数据量：出厂模型 vs 我的 5 分钟微调，抖动同量级。**

| 模型 | 各遍 F0 中位 | 极差 | 平均\|偏离\| | 单遍耗时 |
|---|---|---|---|---|
| 出厂（Emilia 大数据） + 干员报到 | 189 184 184 185 180 | **0.89 半音** | 0.45 | **3.7 s** |
| 微调（38 条/4.8 分钟） + 干员报到 | 192 190 179 178 187 | **1.30 半音** | 0.60 | 7.6 s |

两者差 0.4 半音，在 5 遍样本里就是噪声（同一配置换个时段重跑：1.30 → 2.02）。
⇒ **抖动来自「每次 generate 都重新采样」，不是「训练数据少」**。喂更多数据能让音色/韵律更好，
但不会让「这一遍」和「下一遍」落在同一个音区。微调解决的是吐字与节奏（短句 9.09 → 5.97 字/秒），
不是这个。

**(2) 参考音频：关键不是长度，是「哪一条」。**

| 参考 | 长度 | 靶子 | 各遍 F0 中位 | 极差 | 平均\|偏离\| |
|---|---|---|---|---|---|
| 精英化晋升2 | 4.24 s | 182 | **nan 211 nan nan nan** | — | 2.54 |
| 交谈1 | 13.76 s | 190 | 200 203 196 206 205 | **0.90** | 1.05 |
| 干员报到（当前） | 7.79 s | 180 | 186 187 189 186 209 | 2.02 | 1.04 |
| 编入队伍 | 0.91 s | 199 | 216 191 201 205 201 | 2.12 | 0.57 |
| 行动开始 | 2.51 s | 210 | 235 218 204 217 212 | 2.43 | 0.77 |
| 完成高难行动 | 3.68 s | 192 | 217 236 219 198 194 | 3.41 | 1.73 |
| 交谈2 | 15.95 s | 193 | 209 232 194 218 195 | 3.09 | 1.35 |

* 换参考能把抖动拉开 **近 4 倍**（0.90 → 3.41），但**长度没有单调关系**（16.0 s 的 交谈2 反而 3.09）
  → 「把参考加长/多喂几条音频」不是解，**换一条平静、音区集中的参考**才是。
* ★**发现一条会产出坏音频的参考**★：`精英化晋升2.wav` 5 遍里 **4 遍量不出音高**
  （有声帧 <15%，输出几乎没有浊音段）→ 和 17 节那条「情绪化念白会毁克隆」是同一类问题，
  这类素材要避开。
* ★**5 遍样本不够排序**★：同一个「干员报到」配置两次测量给出 1.30 与 2.02 半音；
  要真的挑参考得每个候选跑 10~15 遍，且**换参考会改音色/节奏（要耳朵复听）+ 每句多等
  0.36×参考秒数**（交谈1 13.76 s ⇒ 每句多花约 2 秒）。

**(3) 结论（写进 README §14 的一句话版）**：这个问题**不值得加数据重训**；
现状（当前参考 + 音区守卫 1.5 半音重采）已经能兜住「整句拔高」；
真要再压，花时间在**挑参考**上（免费），不在训练上。

## 20. 音质第三轮：沙沙声的**指纹**在 10~12 kHz（2026-09-25 晚，用户报「依旧有沙沙声」）

起因：用户说「目前版本依旧有沙沙声」，并且「部署已回退到无训练的参考音频版本」，
同时问「能不能换个模型解决」。这一轮先**量出沙沙声长什么样**，再决定换不换模型。

### 20.1 先纠正一个部署事实：配置回退了，但运行期没有

`config.toml` 的 `clone_dir` 已经指回出厂模型（`sherpa-onnx-zipvoice-distill-*`），
**但 `data/personas/*.json` 里的 `voice_model` 还指着微调目录**，而
`pipeline._apply_reference()` 的规矩是「角色配了 `voice_model` 就用它」→
**一说话就把 `clone_dir` 切回微调版**（`voice_model` 置空才会落回配置里的出厂模型）。
所以「回退」只对没有角色的路径生效，凯尔希/阿米娅实际听到的仍是微调版。
★教训：改 `[tts]` 的默认值不等于改运行期行为，先看角色文件有没有覆盖★。

### 20.2 沙沙声的指纹：**10~12 kHz 那一层掉不下来**（新尺子：频段表）

口径：**只在有声帧**上，算各频段相对 0.3~3 kHz 的平均电平（dB）。
自然语音的高频是**一路滚降**的，沙沙声则是「该掉的那一段掉了但下一段不掉」。

| | 3-4k | 4-6k | 6-8k | 8-10k | **10-12k** |
|---|---|---|---|---|---|
| 真人参考（目标） | −9.0 | −10.7 | −11.3 | −13.6 | **−16.0** |
| 出厂模型（无微调） | −10.6 | −14.4 | −14.7 | −16.3 | **−21.3** |
| 微调模型（实际在用） | −9.0 | −11.6 | −12.2 | −12.3 | **−8.0** ← 翘起来了 |
| Piper（对照） | −10.6 | −16.5 | −21.1 | **−74.5** | **−77.7**（8 kHz 以上直接没有）|

* **微调模型的 10-12 kHz 比它自己的 8-10 kHz 还高 4.3 dB，比真人高 8.0 dB**
  —— 这就是耳朵听到的「沙沙声」。
* 它**不在停顿里**（ZipVoice 的停顿是精确的数字零），而是**骑在语音上的一层高频** →
  这解释了为什么 18.2 的「参考净化」、任何「停顿噪声门」都无效：
  没有噪声可供估计，能动的只有**频谱形状**。
* 出厂模型同口径下比真人还干净（−21.3）；微调版把高频「提亮」了 8 dB —— 微调确实加重了沙沙声。

### 20.3 修法：把搁架**定向**到 10 kHz（旧的 7 kHz/−3 打偏了）

同一段合成音频过不同后处理（天然配对，`sessions/hiss_last/` 可试听）：

| 处理 | 4-6k | 6-8k | 8-10k | 10-12k | 整条高频 |
|---|---|---|---|---|---|
| 微调 · 不处理 | −13.3 | −14.0 | −14.4 | **−12.4** | 11.3% |
| 微调 · **7k/−3（旧默认）** | −13.4 | −15.0 | −17.6 | **−15.5** | 7.1% |
| 微调 · **10k/−9（新默认）** | −13.4 | **−14.3** | **−14.8** | **−22.2** | 7.3% |
| 微调 · 10k/−12 | −13.4 | −14.3 | −14.9 | −26.5 | 7.0% |
| 出厂 · 不处理 | −13.7 | −12.1 | −16.3 | −21.5 | 8.7% |
| 出厂 · 10k/−9 | −13.7 | −12.1 | −16.6 | −30.5 | 7.9% |

* 旧设定为什么「依旧沙」：它把 **8-10k 砍了 3 dB（齿音变闷）却只给 10-12k 降 3 dB**，
  10-12k（−15.5）仍**高于** 8-10k（−17.6）→ 依然翘着。
* 新设定 **10k/−9**：4-8k 完全不动（齿音保住，−14.3 甚至比旧设定好），
  10-12k 落到 −22.2（真人 −16.0）→ 恢复自然滚降。
* ★**耦合警告**★：出厂模型本身 10-12k 已经 −21.5，再来 10k/−9 就闷到 −30.5 →
  **若把角色回退到出厂模型，这一项要调回约 −4 或直接关掉**（所以「换模型」和「这项」要么一起改，要么用 `--profile` 量一遍）。

### 20.4 「换个模型能不能解决」——能，但没必要先换

* **Piper 给出的天花板**：它的 8 kHz 以上是 **−75 dB**（约等于没有）——所以它「彻底不沙」，
  代价是**没有 8 kHz 以上的内容**（22.05 kHz 模型、带限），听感偏闷；而且它不支持零样本克隆。
* 想「既保凯尔希音色又彻底不沙」只有两条：
  **① 给角色微调 Piper/VITS 声线**（路线 C，环境半成品已就绪；代价 = 下载 huayan ckpt
  + clone piper 仓库 + 纯 CPU 训练数小时；收益 = RTF 0.05、开口 0.13 s、声码器干净）；
  **② 换 ZipVoice 的声码器**（现在只配了 `vocos_24khz.onnx`；换别的要 mel 配置匹配，
  且没有现成的同规格替代品，风险高）。
* 结论：**这一轮的沙沙声不用换模型就能治好**（定向搁架，零下载、零延迟代价）。
  换模型值得投资的地方是**速度**（Piper RTF 0.05 vs ZipVoice 2×1.2）和「结构上不可能有高频噪声」，
  不是这一项。
