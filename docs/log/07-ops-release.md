### 30.3 ① 切短：`scripts/tools/prepare_piper_segments.py`（长独白 → 一句一条）

体检结论是「数据又少又长」（30 条 / 4.7 分钟、平均 9.4 s、12 条超 10 s），
而 **Piper 的配方吃的就是短句**。所以写了这个脚本：VAD 切段 → 每段 ASR 转写 →
**把转写与原文对齐**，标签用原文。

★踩了三个坑，都写在文件里★：
1. **位置会串**：一开始想用 `segmenter.accept()` 的返回值定位，但它一次只吐一段，
   一次调用产生两段时第二段要等下次 —— 那时「已消耗样本数」已经往后跑了。
   改成用 `speech_detected` 取**逐帧掩码**，分组和位置都自己算。
2. **逐段映射会漏字**：第一版给每段各自映射原文范围，结果 ASR 漏听的字在原文里变成空洞
   （`任命助理_01` 成了「是请坐。」，`3星结束行动_01` 只剩「2、」）。
   → 改成**只在对齐给出的位置下刀**，原文被切成连续区间，于是得到一条可断言的不变量：
   **各段标签拼起来 == 原文（一个字符不差）**。
3. **切点会漂到词中间**：拿转写的字数当切点依据，转写一漏字就漂（出现过「博士我」「会大」）。
   → 改用**每段时长比例**（同一个人语速基本恒定，比转写可靠）+ **标点吸附**
   （在 ±3 个字内找标点，切在标点后面）。之后标签就都是完整句子了。

排除法一条条走（每一条都留了可复现的命令）：

  `行动开始_01.wav`（比值更低）单独却不崩。
* `C:\msys64\mingw64\bin\gdb.exe -batch -ex run -ex "bt 40" --args ...`：拿到
  `[Thread ... exited with code 3221225477]` —— **崩在 worker 线程**，

**最终结论（实测，可复现）**：崩溃与**短片段**相关 ——
* 87 条（0.39~4.8 s）→ 崩；65 条（比值 ≥0.9）→ 崩；42 条（≥1.5 s）→ 崩；
* **38 条（≥2.0 s）→ 能训**；**24 条长片段 → 能训**（同一台机器、同一份代码）。

**没查清的**：确切触发机制（Cython 那份 `maximum_path_each` 里 `index = t_x - 1` 在

★教训★：**「切短」这个方向没错，但 Piper 这份 VITS 实现吃不了太短的片段**。

### 30.8 ★更正：崩溃的真正根因是**我自己把标签配错了**（不是「短片段」）★

30.4 那节的结论（「短片段会崩」）是**错的**，这里更正 —— 因果链是这样被翻过来的：

把护栏 `--min-frames-per-id` 默认值写成 0.9 之后，发现 `kaltsit_short` 从 38 条**被剔到只剩 8 条**，
训练 5 分钟就"完成"了。于是去量「梅尔帧数 / 音素 id 数」的分布：

| 数据集 | 比值 最小 / 中位 / 最大 | 说明 |
|---|---|---|
| `kaltsit_long`（老口径长片段） | 1.01 / **1.91** / 2.41 | 正常 |
| `kaltsit_short`（`--min-seconds 2.0`） | 0.18 / **0.72** / 1.16 | ★文本比音频长了约 2.65 倍★ |

**根因**：`prepare_piper_segments.py` 把 `min_seconds` 交给了 `mask_to_regions` ——
于是短片段在**标文本之前**就被删了，而标签是按「留下来的片段各自时长占比」分配全文的
→ 每个留下来的片段都分到了被删片段的那份文本。**每条数据的文本都比它自己的音频长一倍多。**

**修正**：先切出全部片段 → 标完文本 → 最后才筛（被丢的片段连同它那段文本一起丢）。
修完重跑：`kaltsit_split`（`--min-seconds 1.0`）**69 条 / 比值 0.80 ~ 1.75（中位 1.02）**，
**烟雾测试 2 个 epoch 直接通过（EXIT=0，271 秒）**。

所以**「≥2.0 秒」只是碰巧把比值抬上去的代理条件**；真正的因果是
**文本长度超过音频帧数 → `monotonic_align.maximum_path` 的路径写越界**（就是 30.4 里
一直怀疑的那条，只是我一开始把矛头指向了「时长」而不是「标签」）。

★教训（这条比崩溃本身值钱）★：
1. **「先筛选再标文本」是个静默的错误** —— 不报错、不崩（在别处），只是让模型学歪。
   凡是「按比例分配」的东西，**筛选必须在分配之后**。
2. **护栏阈值必须用分布来定**：0.9 看着"保守"，实际把数据剔掉 79%（还是静默的）。
   现在默认 **0.7**（长片段一条不剔、切短集一条不剔），且**剔掉超过 25% 就大声报警**。
3. **崩掉的东西比"悄悄变差"好查** —— 这次是靠"训练 5 分钟就完成"这个反常现象翻出来的；
   如果护栏没报警、训练正常跑完，我会拿着 8 条样本的模型去下结论。

### 30.10 ★再更正一次：崩溃是**概率性**的；改成「崩了也不心疼」（`train_piper_forever.py`）★

§30.8 把根因归到「标签配错」，**不完整** —— 修好标签并把比值拉回 1.02 之后：

* 烟雾测试（同一份 69 条数据、2 个 epoch、18 步）→ **通过**；
* 正式跑 B 组（同一份数据）→ **25 步之后照样崩**（`0xC0000005`）；
* 同时跑的 C 组（**同一份数据、同一份代码，只差学习率**）→ 跑到 26 步**没事**，还在跑。

同数据同代码一个崩一个不崩 ⇒ **崩溃是概率性的**，不是「某条样本必崩」。
回头再看前面那些「能训 / 不能训」的结论，其实都是**概率**的差别（长片段 24 条样本量小、
每步只有一个 batch 组合，撞上的概率低）。

**没查清的确切机制**（老实说）：怀疑与 `rand_slice_segments` 每步随机抽的切片位置有关
（它按 `ids_slice * hop_length` 去切 8192 个采样点，抽到边界情形就可能出问题），
但没抓到证据。**继续深挖的性价比不高**，因为：

> **做不到「让它不崩」，就做到「崩了也不心疼」** —— `scripts/tools/train_piper_forever.py`

看门狗的做法：每次跑完检查退出码，**非 0 就自动从最近的那个 checkpoint 续跑**，
最多重启 30 次；每次崩溃最多损失 `--checkpoint-epochs` 个 epoch。
★注意★ 续跑是「只搬权重、不恢复优化器状态」（`train_piper.py --checkpoint` 的语义），
对 lr 1e-5 量级的微调可以接受，但**别把它当严谨的断点续训**。

三个臂现在的配置：

| 臂 | 数据 | 学习率 | 目标 | 看门狗 |
|---|---|---|---|---|
| A | `kaltsit_long` 24 条（比值 1.91） | 1e-5 | 1800 步 | ✓（从 epoch 29 续） |
| B | `kaltsit_split` 69 条（比值 1.02） | 1e-5 | 1800 步 | ✓ |
| C | `kaltsit_split` 69 条 | 1e-4 | 540 步 | ✗（当时没崩，就让它跑） |

★教训★：**遇到「无 traceback 的原生崩溃」，先建立「重启 + 续跑」的能力，再去挖原因。**
这次是反过来做的（先挖了三小时原因），而看门狗半小时就写完了 —— 而且它让剩下所有实验
都不再受这个 bug 影响。


### 30.11 ★★最终根因：不是数据、不是短片段，是**内存不够**（有 traceback 为止）★★

看门狗（§30.10）第一次就抓到了一份**真正的 Python traceback**（B 组第 2 次尝试"只"退出码 1）：

```
MemoryError                              ← torch.save → zip_file.write_record
  ...
ModelCheckpoint._save_checkpoint → torch_io._atomic_save → torch.save(checkpoint, bytesbuffer)
RuntimeError: [enforce fail at inline_container.cc:672] . unexpected pos 651145984 vs 651145876
```

**机制**：`lightning_fabric.utilities.cloud_io._atomic_save` 会**把整个 checkpoint 先序列化进
内存缓冲区**（`torch.save(checkpoint, bytesbuffer)`）。内存紧的时候这个写入会失败 ——
抛 `MemoryError` 是运气好的情况；**在 C++ 里分配失败就直接变成 `0xC0000005` 访问违例**
（没有 traceback、崩在 worker 线程）—— 这就是前几小时看到的一切。

当时的实际内存（31.5 GB 总）：

| 进程 | 占用 |
|---|---|
| `llama-server`（本地大模型 / Ollama） | 4942 MB |
| 训练 A / 训练 B（**提交内存**） | 5456 MB / 4448 MB |
| VS Code（4 个进程） | ~6300 MB |
| IntelGraphicsSoftware / WorkBuddy / Memory Compression | 2403 / 1187 / 976 MB |
| **可用** | **3.9 GB** ← 就是这么被挤干的 |

**这解释了全部"矛盾"**：为什么"与学习率无关、与并行无关"；为什么**概率性**（取决于当时有多少空闲内存）；
为什么崩溃常在 ~40 秒（`--checkpoint-epochs 1` 时那正是第一次存档的时刻）；
为什么我"测出"的「≥2.0 秒能训、切短的不能训」都是**伪相关**（不同数据集在不同时刻跑，
当时机器上跑着别的进程/别的臂，空闲内存不同）。

**修三处**：
1. `train_piper.py` 的 `ModelCheckpoint(save_weights_only=True)` —— 只存权重。
   续跑本来也只需要权重，而且**把存档内存峰值砍一半**（cpkt 60 MB → 30 MB）。
   （连带要改 `load_weights`：`save_weights_only` 存的文件**本身就是 state_dict**，外面没有那层壳。）
2. `train_piper_forever.py` 每次重启打印**可用内存**，低于 3 GB 直接警告。
3. 不再 3 个臂并行（§30.9 那样 3×4 线程 + 3 份模型 = 15 GB 伺候）；只留 2 个。

★三条教训（这条比前面所有结论都值钱）★：
1. **"没有 traceback 的原生崩溃"要先怀疑资源**（内存/句柄），再怀疑数据和代码 ——
   数据错误会报错，资源不够才是不讲道理的崩。
2. **先建"重启+续跑"能力**（§30.10），再挖原因：正是它把这次唯一的 traceback 抓回来的
   （一次干净的退出码 1 夹在两次硬崩之间）。
3. **我自己造出的伪相关**：「≥2.0 秒能训」验证了三次都成立，于是我把它写成了结论 ——
   其实两边跑的时候机器负载不同。**验证一个规律时，必须让"其他条件"真的保持不变**，
   否则三次"验证成功"也可能只是三次碰巧。

   **是被跟踪的文件**，这 28 个提交正好改了它们。而且同类的旧数据（`data/alarms.json`、

   不是"即将泄漏"，是"已经有一份在上面，现在还要再来一份更新版"。

**先扫了一遍**：凭据零命中（`sk-` / `ghp_` / `AIza` / 私钥 / 密码赋值 / `Bearer` 全 0 命中）；
`data/vision/` 的运行截图**从未进过任何历史**（当初的 .gitignore 生效了 ✓）；
远程树里没有图片 / 音频 / 模型文件。

**用户选择**：C —— 连历史一起清，再强推。

**做法**（全库 87 个提交，其中 9 个碰过这 4 个文件）：

1. 先打整库备份包，放在项目外：`git bundle create D:\local_assistant_backup_pre-rewrite.bundle --all`（1.0 MB）。
2. `git filter-branch --force --index-filter "git rm -r --cached --ignore-unmatch <4 个文件>" --prune-empty --tag-name-filter cat -- --all` → 87 → 85 个提交。
3. `.gitignore` 补规则（4 个文件名 + `data/*.bak`，迁移时改名的旧文件内容同样是日程），提交。
4. 清本地旧对象：删 `refs/original` → `git reflog expire --expire=now --all` → `git gc --prune=now`。
5. `git push --force-with-lease=main:eadc5a4… origin main`。

**踩到的 4 个坑**（都值得记）：

1. ★**`filter-branch` 会把工作区同步成新的 HEAD** → 那 4 个文件**从磁盘上一起消失了**。
   `--index-filter` 名义上"只动索引"，但收尾时 filter-branch 会 reset + checkout，
   被剔除的文件在磁盘上也没了。**救命的是 `refs/original/refs/heads/main`**（重写前的指针，
   只要还没删就能捞回来）：
   `git checkout refs/original/refs/heads/main -- data/events.json data/memos.json` → `git reset`，
   再用 `git hash-object` 和 `git rev-parse <tree>:<path>` 比对，**blob 哈希一致 ✓**（内容无损）。
   → **教训：重写历史前，先确认"个人数据在工作区之外另有副本"，或者干脆先复制一份出来。**
2. `git checkout <tree-ish> -- a b c d` 里**只要有一个 pathspec 不存在，整条命令一个文件都不写**
   （`alarms.json` / `schedule.json` 早已被应用改名成 `.bak`，于是连 `events.json` 都没还原成功，
   还看不出来）。→ **先 `git ls-tree -r <tree> --name-only` 确认哪些路径真的在，再 checkout。**
3. **`--force-with-lease` 在 `reflog expire` 之后会以 "stale info" 失败**（它靠 reflog 判断
   "你上次 fetch 到的是什么"，reflog 被清就失去依据）。另外 `filter-branch -- --all`
   **会把 `refs/remotes/*` 也一起重写**，本地 `origin/main` 已经不是远程的真实值。
   → 用显式期望值：`git push --force-with-lease=main:<远程当前 SHA> origin main`。
4. PS 5.1 的 `Invoke-WebRequest` 会**弹"是否要解析网页脚本"的确认框**，把循环里的判断全污染了
   （一度看错，以为旧路径也 404）。→ **验 HTTP 状态用 `curl.exe -s -o NUL -w "%{http_code}"`**。
   （另外 PS 5.1 读 UTF-8 的 json 会显示成乱码，那是显示问题，别当成文件坏了 —— 用 Python 读。）

**结果**：`main` 由 `eadc5a4` → `4f69632`（forced update）✓；远程历史与远程树里这 4 个文件**零残留** ✓；
`raw.githubusercontent.com/.../main/data/{events,memos}.json` 都是 **404** ✓。

**残留风险（如实记，别以为"重写历史 = 什么都没发生"）**：

- 旧提交 `eadc5a4` 在 GitHub 上**仍可通过 SHA 直接访问**（不可达对象，GitHub 还没 GC 掉）：
  `.../eadc5a4/data/memos.json`、`alarms.json`、`schedule.json` → **HTTP 200 仍能抓到**；
  `events.json` 是 404（那个提交里它还不存在，一致）。
- 没有 ref 指向它，网页历史里看不到，但"知道 SHA 就能取"。要彻底清得**给 GitHub Support 发工单**
  （他们能强制回收不可达对象），否则只能等它自己被 GC。
- 9/24 那份已经公开了约 5 天：搜索引擎、缓存、别人的 clone 都管不着。
  → **重写历史不能"召回"已经泄漏的内容，只能阻止它继续存在。**

## 55. 可交付化：从「只有源码」到「能一键装、能安全升」（2026-10-08）

用户贴了一篇「GitHub 上的源码项目 vs 一键安装的软件，本质区别是什么、怎么让自己更像软件」
的长文，然后说：**对我们的项目做可用性优化**。这一节就是这件事，以及为这个项目做的取舍。

### 55.1 先量家底：我们有什么、缺什么

| 维度 | 动手之前 | 缺口 |
| --- | --- | --- |
| 版本 | `voice_loop/__init__.py` 里一个 `1.0.0`，**没有 tag** | 没人知道手上是哪一版；发布包无从命名 |
| 安装 | README 里六条手工命令（pip → 下模型 → ollama pull → selftest） | 新人第一步就要读完整节，错一条就卡住 |
| 依赖 | `requirements.txt`（必需/可选混在一份里） | 缺了哪个包只能等运行时报错 |
| 模型 | `scripts/download_models.py` 能按组下 | 与「装依赖」「体检」之间没有串联 |
| 配置 | `config.toml` 在 git 里，`load_settings` 缺文件直接抛 | 没装好的机器上什么都跑不起来 |
| 升级 | **没有**，只能手工 `git pull` + 猜要不要重装依赖 | 「升级会不会把我日程弄没」没答案 |
| 制品 | **没有**，只有仓库 | 用户没有「下载一个包」的入口，也没有校验和 |
| 自检 | `scripts/check_deploy.py`（很好用） | 藏在一个脚本路径里，新人找不到 |

一句话：**开发架构齐全，交付面为零**。这正是那篇长文说的「源码分发 vs 制品分发」。

### 55.2 做了什么

1. **版本号只有一个地方写**：根目录 `VERSION` → `voice_loop.__version__` → `main.py --version` →
   发布包名 → `latest.json`。四处引用一处定义（写四遍迟早对不上）。
2. **三条命令**（`python main.py setup | doctor | upgrade`），逻辑全在
   `voice_loop/setup_flow.py`：★只依赖标准库★，因为它的第一个用途就是「依赖还没装齐」。
   为此 `main.py` 把 `voice_loop.audio` 那串重导入包进 try，并允许
   `setup/doctor/upgrade` **缺 config.toml 也能跑**（`settings_or_default`）。
3. **升级的三条安全边界**（写进代码，也写进 README 3.4）：
   ① 动手前**先备份**（`data/*.json`、`personas`、`knowledge`、`memory`、`config.toml` →
   `data/backup/upgrade-<时间>-<sha>/`，附 `MANIFEST.txt`（逐文件 sha256）与 `RESTORE.txt`
   （不依赖本工具的还原命令））；② 工作区脏就**停**（`git pull` 结果不可预测，叫你先 stash）；
   ③ 任何一步失败都打印 `git reset --hard <升级前 sha>` 与备份路径。
   `upgrade` 默认**只检查**，`--apply` 才动；`--restore` 默认也**只列**。
4. **`install.ps1`（Windows 一键）**：只做三件事 —— 拿到代码 / 建 `.venv` + `pip install` /
   回调 `main.py setup`。★壳里故意只有这么点逻辑★：`.ps1`/`.cmd` 是这个仓库的坑王
   （中文、引号、编码，五次以上），所以判断全在能被离线自测钉住的 Python 里。
   它**必须带 UTF-8 BOM**（PowerShell 5.1 否则按 GBK 解析中文），文件头写了警告，
   另给 `-DryRun` 让人先看它要干什么。
5. **`scripts/make_release.py`：制品 = zip + sha256 + `latest.json`**。
   文件清单来自 `git ls-files --cached --others --exclude-standard` —— 于是
   `data/`（用户数据）、`models/`、`sessions/`、`.venv*` 天然不进包，**与 `.gitignore`
   永远是同一套规则**，不会两处打架；打包前还会拦「缺关键文件」。
6. **离线自测 `scripts/tests/test_setup_flow.py`（7 节）**：钉的不是「功能好用」，是**边界**——
   非 git 目录里升级要好好说话、拉不到远端时**一个字节都不许写**（连备份目录都不建）、
   备份不许漏也不许把 `models/` 卷进来、还原默认必须 dry-run、发布包里不许混进
   `models/sessions/.venv`、以及最后那道闸门「真实仓库没被动过」。

### 55.3 实测抓到的四个真东西

1. ★**子进程编码**★：接上 `doctor` 后，体检里那条中文警告在我这儿变成了 `????`。
   原因见工程日志反复写过的那条 —— **Windows 上子进程的 stdout 接进管道时按 GBK 编码**，
   父进程按 UTF-8 解码，中文静悄悄坏掉（不报错）。我自己的记忆里就写着这条，还是又踩了一遍。
   修法：`child_env()` 统一给子进程 `PYTHONIOENCODING=utf-8` + `PYTHONUTF8=1`。
2. ★`git tag --list <不存在的 tag>` 退出码是 0★：第一版发布脚本拿退出码判断「tag 打没打过」，
   于是它对新 tag 说「**这个 tag 已经存在**」——反了。改成看输出，并写进自测。
3. `Set-Content -Encoding utf8` 给 `scripts\tests\run_all.cmd` 加了个 BOM：`.cmd` 第一行会因此解析
   失败（这条也在记忆里）。已去掉 —— 动 `.cmd` 之后**必须**检查一遍头三个字节。
4. `load_settings` 缺 `config.toml` 直接抛：而「还没装好」正是 `setup` 要处理的状态，
   所以给 bootstrap 命令单独开了一条「读不到就用默认值」的路。

### 55.4 没做的，以及为什么不（诚实清单）

- **Docker / Compose / Helm**：这个项目要**麦克风 + 声卡**、要 3~4 GB 本地模型、要 Ollama、
  要 Windows 的关屏/字幕点穿（关屏 2026-11-20 已删，见 §64.1）；容器化收益小、坑多（`/dev/snd` 透传、镜像体积、
  模型挂载）。**只有控制台是天然可容器化的**（纯网页 + 读写 json）—— 想做的话那是最值得的一步。
- **内置自动更新**：自托管工具不该偷偷换自己的代码。现在是「默认只检查、`--apply` 才升、
  升级前先备份」，把决定权留给人。真要做也应该是「通知 + 一键」，不是静默。
  → ★第 56 节已按这个原则做了★：`python main.py update` 与非 git 安装的控制台「更新」标签
  （先备份 → 校验 sha256 → 只覆盖程序文件），仍然默认**只检查**，动手要显式确认。
- **签名 / SBOM**：现在有 sha256 与 `latest.json`，够本机自用与「下载后核对一下」。
  要对外分发再上 `cosign`/Sigstore——那需要发布渠道稳定下来才值得。
- **单文件 exe（PyInstaller/Tauri 壳）**：能省掉「装 Python」这一步，但模型路径、原生库
  （PortAudio/onnxruntime）、以及「代码随时改」的开发习惯都要重新设计，是另一个量级的事。
  → ★第 56 节把「控制台」这一半做了★（50 MB、不加载模型、不碰音频设备）；
  **语音服务仍然不冻**（几 GB 模型 + 外部 Ollama + 音频设备），理由见 56.9。

### 55.5 现在的交付面（对照「L0~L5」那套分层）

| 层次 | 这个项目 |
| --- | --- |
| L0 源码 | `git clone` + 六条命令（仍在，README 3.2） |
| L1 脚本 | ★`install.ps1`（幂等、`-DryRun`、BOM、只碰 venv/pip）★ |
| L2 制品 | ★`make_release.py` → 源码 zip + sha256 + `latest.json`★（下载即用，含 `config.toml`） |
| L3 自检 | ★`main.py setup / doctor`★ + `check_deploy.py`（同一份判断） |
| L4 生命周期 | ★`main.py upgrade`（备份→拉取→依赖→模型→自检→回滚指令）、`--restore`★ |
| L5 自动更新通道 | 有意**不做**（见 55.4）；`latest.json` 已经是将来做它的地基 |

## 64. 删掉「熄屏」、加上「天气」（2026-11-20，用户要求「清除熄屏功能，然后增加天气工具，参考成熟实现」）

### 64.1 为什么删熄屏

它是个**成本全在维护面、收益在键盘旁边**的功能：三个平台各一套
（Windows `SC_MONITORPOWER` 广播、Linux `xset dpms`、macOS `pmset`），
Wayland 还永远做不到、只能回一句「请用桌面快捷键」；外加 `[skills] allow_system_commands`
一个开关挡着它。删掉的东西一次说清：

| 位置 | 删了什么 |
|---|---|
| `voice_loop/system_ops.py` | 整个文件（`monitor_off` / `monitor_on` / `supported`）；`platform_name` 与 `power_info` 挪进 `scripts/check_deploy.py`（唯一真正的使用者是体检报告） |
| `voice_loop/skills.py` | `_handle_screen` + 两张词表 + `handle()` 里的一行 + 「帮助」里的那句介绍 |
| `voice_loop/settings.py` / `config.toml` | `[skills] allow_system_commands` |
| `scripts/check_deploy.py` | 「6 平台能力」里那两条「关屏幕可用 / 不可用」 |
| 自测 | `test_skills_route` 的关屏段、`test_vision` 的「关屏幕不会被看图抢走」、`test_precision` 的 `system_ops` 段 |

★保留的判断★：`platform_name()` / `power_info()` 还在体检里（换系统前想知道「现在什么供电、
什么系统」是有用的），但它们现在**只读**，不再有「动一下显示器」的能力。

### 64.2 天气：为什么选 Open-Meteo，怎么分层

成熟 harness agent 的 `get_weather` 都是同一个形状：**地名 → 经纬度 → 预报**，两跳。
数据源选 **Open-Meteo**：免 key、免注册、家用频率随便用，Geocoding 与 Forecast
两个公开接口就够。没用收费 API 的原因不是钱，是**没网就该说没网**——
多一个 key 只会让「查不到」多一种原因。

新文件 `voice_loop/weather.py` 分三层，和 `asr/`、`tts/` 一样可以单独拿走：

| 层 | 函数 | 为什么单独一层 |
|---|---|---|
| 解析 | `parse_scope` / `parse_place` | 纯字符串、纯确定性，一张表就能改；「明天上海要带伞吗」→（明天，上海）不依赖模型 |
| 取数 | `geocode` / `forecast` | 直接对应两个 HTTP 跳；返回原样保留，不在这里加工 |
| 说话 | `describe` / `code_text` | 数值 → 能念的中文（`12 到 21 度`、`降水概率 80%，记得带伞`），不念 `°C`、不念 WMO 编号 |

门面 `WeatherService` 管三件事：**缓存**（同一地点 10 分钟）、**地点优先级**
（原话里的地名 → 配置经纬度 → `default_city` → `auto_ip`）、**把失败说人话**
（断网 / 地名查不到 / 功能关着，三种话术不同）。

接了三处，共用同一份解析：

1. **技能层**（本地角色也能用，零延迟）：`_handle_weather`，词表命中就走。
2. **工具层**（模型先路由那条路）：`weather` 工具，参数仍然只有 `text`（原话）。
3. **MCP harness**（API 角色）：`agent` 服务器加 `weather`，预设里加 `weather` 并进 `harness`；
   大肥鱼的 `api_tools` 因此多了 `weather`。

### 64.3 踩到的两个坑

- ★`看看天气` 会被「看图」抢走★：`_handle_vision` 认 `看看` 开头的句子，所以
  `_handle_weather` 必须排在它**前面**（`handle()` 的顺序就是优先级，注释里也写了原因）。
- ★「火星」真的查得到★：Open-Meteo 的 geocoding 会返回广东的「火星」村 ——
  这不是 bug，是地名库的真实行为。所以工具描述里写明「地名由本地代码解析，不要自己换经纬度」，
  而不是让模型去猜。

### 64.4 隐私与默认值

- `[weather] auto_ip` **默认 false**：打开就等于告诉 `ipapi.co`「这台机器在哪」。
- `default_city` 在仓库里留空（不把用户常住城市提交上去），本地要就直接写
  `config.local.toml`（已在 `.gitignore`）。
- 断网时**只说查不到**，绝不编温度 —— 和记忆层「宁可查到空也不要凭印象说」是同一条规矩。

## 65. 托盘图标：给「没有窗口的服务」一个能关掉它的入口（2026-11-20，用户要求「为服务增加托盘小图标，可以右键选择停止服务」）

### 65.1 为什么这件事值得做

`listen -B` 起来的是 `pythonw.exe` 进程：**没有控制台窗口、没有任务栏按钮**。
于是「怎么关掉它」过去只有两条路 —— 记住 `python main.py stop`，或者去任务管理器里
翻一堆同名的 pythonw。托盘图标是第三条：右下角右键 → 停止服务。

### 65.2 两种模式，为什么不是一种

| 模式 | 谁在跑 | 多出来的菜单项 | 适用 |
|---|---|---|---|
| `embedded` | 图标就在**服务进程内**（`listen` 启动时顺手起） | 隐藏图标 | 日常：图标在 = 服务在，停服务时图标自己消失 |
| `standalone` | `main.py tray`，**独立进程** | 启动服务 / 退出托盘 | 服务停了图标还在，能从菜单里再起回来 |

先把「图标跟着服务走」定成默认：否则会出现「服务早停了，图标还挂着，点什么都说不通」
这种更难解释的状态。需要反向控制时再显式跑 `main.py tray`（有 `sessions/tray.pid`
单实例保护，不会长出第二个图标）。

### 65.3 停止是怎么生效的（★不是 kill，但也不是只写个文件★）

1. 写 `sessions/listen.stop` —— `pipeline` 的常驻循环每轮开头都看它，看到就收尾退出；
2. **同时**起一个看门狗线程：`[app] tray_stop_grace` 秒（默认 20）内进程还在，就
   `taskkill /F`。

第 2 步是被实测逼出来的：`pipeline.close()` 在关扬声器流那一步会等 PortAudio 播完缓冲，
实测 **7.1 秒**；服务正在回答一个长回合时更久（ASR 复核 + TTS 音区重采，实测有 100 秒的
回合）。只写文件的话，用户点「停止」之后要盯着一个还在说话的服务，看起来就是「点了没反应」。

### 65.4 顺手补的诊断：收尾每步耗时

以前日志最后一行总是「TTS 已卸载」，然后就没下文了 —— 到底卡在哪一步只能靠猜。
现在 `close()` 会给每一步打点：

```
[收尾] 扬声器 7.1s / 麦克风 0.3s / 识别 0.0s / 唤醒 0.0s / TTS 0.0s / LLM 0.0s
```

第一次跑就定位到「慢在关扬声器流」这个结论（不是模型卸载、也不是记忆同步）。

### 65.5 踩到的坑

- ★pystray 的 action 只认 0/1/2 个参数★：`lambda _icon, _item, _id=entry.id:` 是 **3 个参数**，
  pystray 用 `co_argcount` 判断，直接 `ValueError`。必须包一层 `def action(_icon, _item)`。
- ★`Shell_NotifyIconGetRect` 用 `uID=1` 查不到★：pystray 用默认 `uID=0`。查 1 会得到
  `E_FAIL`，看起来像「图标没加上」。
- ★Windows 11 默认把新图标藏进「^」里★：不是没起来，是没露脸。文档里写了怎么拖出来。
- 顺手删掉了 `voice_loop/console/tray.py`：它是上一轮留下的**没人 import 的草稿**
  （也从未入库）。里面「为什么用 pystray 而不是裸 ctypes」的论证搬到了新模块顶部。

### 65.6 验证

- `scripts/tests/test_tray.py`（离线，不弹窗口、不停真服务）：两种模式的菜单与可用状态、
  停止写的是**停止文件**（不是 kill）、宽限期到点才强杀（用注入的 alive/kill 验）、
  服务自己退了就不强杀、打开控制台/日志走注入回调、图标尺寸与两种状态、没装 pystray 的退路、
  单实例锁。
- 真机：`listen -B` 起服务 → 日志出现「[托盘] 已就绪（embedded）」；
  `Shell_NotifyIconGetRect` 能查到我们的图标（hr=0，位于隐藏区）；
  写停止文件 → 服务 7~8 秒内退出并打印收尾耗时；`_kill_pid` 单独在一次性进程上验过。

## 66. 邮件子系统：读可以自动，写必须过人（2026-11-20，用户要求「让 agent 帮我管理邮件，区分重要程度，收到重要邮件时提醒我」）

### 66.1 是「一个工具」还是「一个子系统」

用户自己也拿不准，所以先按成熟做法查了一遍再定：MCP 官方 email server 是"allowlist-first"（默认
只能读白名单里的地址）、Exchange Online 已经**彻底关掉 basic auth**、Graph 的增量同步要走
`delta query`（否则每轮只能全量拉）。三件事都说明这不是「包一层 HTTP」的量级。

于是定成**子系统**（`voice_loop/mail/`）+ **5 个 MCP 工具**，但不拆成独立仓库：

| 拆出去的好处 | 留在这里的好处 |
|---|---|
| 可以脱离语音单独跑 | 提醒要弹窗 + 念一句、发信要弹审批卡 —— 这些能力本项目已经有了 |
| 依赖更干净 | 已经分好的 `asr/` `tts/` `memory/` 就是"包内子系统"的先例 |

它现在也进边界自测：`mail/` 里不许 import `tts/asr/memory/skills/pipeline/...`，
**弹窗、朗读、审批卡全部是注入的**（`toast=` / `speak=` / `on_draft=`）。

### 66.2 发信为什么非得点按钮

发信是**不可逆的外部动作**。把「批准」写成提示词里的一句"发送前先问我"是不可靠的：
模型完全可以在同一轮里自己"问"自己再"答"。

所以闸门写在代码路径上（`outbox.Outbox.send`）：

| # | 闸门 | 默认 |
|---|---|---|
| 1 | `[mail] allow_send` = true | **false** |
| 2 | 收件人在 `[mail] send_allowlist` 里 | **空表 = 谁都发不出去** |
| 3 | 状态必须是 `approved`（用户点过按钮） | — |
| 4 | `confirm_token` = HMAC(草稿 id + 正文 hash + 过期时间) | 5 分钟过期 |

第 4 条是针对"批了 A 版本、偷偷改 B 版本再发"的：正文变一个字，hash 就对不上。
token 只在用户点「发送」那一刻由**本进程**签发 —— 模型这条路径上根本拿不到。

顺带把「网络断在半路」单独出来：状态标 `unknown`，**不自动重试**（可能已经发出去了），
由人去看 Outlook 的「已发送」。这是唯一一处宁可"人工兜底"也不"智能重试"的地方。

### 66.3 重要度：规则先算，模型只补充

`[mail] high_score / medium_score` 两档阈值 + 规则分（VIP、优先域名、只发给你、
会议/截止/缴费类词）+ 模型返回的 JSON（一句话概括 / 要不要回 / 截止时间）。
模型判定"像群发"会**降权**，所以促销邮件不会因为写了"紧急"就弹窗。

隐私边界：**只把「主题 + 发件人 + 前 `classify_chars`（默认 400）字」发给模型**，
整封正文不出本机；想零外发就 `classify_model = "ollama:qwen3.5:4b"`。

### 66.4 同步：别用 delta 做第一次

第一次就 `delta` 会从"邮箱创建那天"开始翻页（几千封、几十页）。所以：
先 `$filter=receivedDateTime ge <N天前>` 拉一个窗口（`first_sync_days` 默认 30），
再取 `$deltatoken=latest` 当游标接力；之后每轮只问"变了什么"。
游标过期 Graph 返回 **410** → 自动按窗口全量重来一次（不丢信，也不重复入库）。

### 66.5 Azure 应用注册：踩了一路坑（留给下一次）

| 坑 | 现象 | 真相 |
|---|---|---|
| 找不到 App registrations | 门户首页没有这个入口 | 它在 **Entra ID**（`entra.microsoft.com`）里，不在 Azure 门户首页 |
| 保存 manifest 失败 | 改 `signInAudience` 就报错 | 个人账号受众要求 `api.requestedAccessTokenVersion = 2` |
| 设备码报 `AADSTS7000218` | 说没开公共客户端 | 清单字段叫 **`isFallbackPublicClient`**（Graph API 才叫 `allowPublicClient`） |
| `AADSTS9002346` / `9002332` | 一会儿说只支持个人、一会儿说只支持组织 | `signInAudience` 与 `[mail] tenant` 必须**成对**改（见 guide/mail.md 的对照表） |
| 学校账号登录被挡 | 「需要管理员批准」，门户上「授予管理员同意」是灰的 | 租户不允许用户自同意，非管理员无解 → 三条绕路：转发到个人邮箱 / 让 IT 批一次 / 装经典 Outlook 走本机 COM |

最后一条是当前的**阻塞点**：学校账号（`@connect.hkust-gz.edu.cn`）需要管理员同意，
用户不是管理员。代码这一侧已经和"数据源"解耦（`adapters.py` 是唯一知道外面世界的文件），

### 66.6 验证

### 66.8 服务跑起来才暴露的第三个 bug：游标一直是空的（每 3 分钟全量重拉）

服务起来后的第一轮巡检日志：

```
[mail] 巡检已启动（每 180s）
[mail] 同步完成：新增 0、更新 276（全量 6 页）
```

「全量」不该出现在第二轮之后。查下去发现 `delta_cursor_from_now()` 用的是
`?$deltatoken=latest` —— 那是**旧版 Outlook REST** 的写法，Graph 的 `/messages/delta`
现在不认：返回的对象里没有 `@odata.deltaLink`，函数老老实实返回空串，
于是 `Syncer` 每轮都走 `_run_first()`（按时间窗口重拉 6 页）。

后果不致命但很浪费：每 3 分钟一次 6 页请求，276 封邮件重复 upsert，还容易撞 Graph 限流。

修法：唯一可靠的拿游标方式是把 delta **翻到最后一页**（`$select=id`，不要正文），
最后一页才带 `@odata.deltaLink`。实机翻了 21 页拿到，之后增量一轮 1 页、2.3 秒：

```
[mail] 取到增量游标（翻了 21 页）
[mail] 同步完成：新增 0、更新 0（增量 1 页）
```

信箱特别大（`max_pages` 30 页还没到底）时返回空串、继续按时间窗口同步 —— 功能不受影响，
只是慢一点。自测里钉住了三条：跟着 `nextLink` 翻页、翻到最后一页才返回、翻不到返回空串。

### 66.9 端到端实测：一句话 → 弹卡 → 点「发送」 → 真的发出去了

服务跑着（PID + 托盘），通过控制台信箱投一句自然语言给大肥鱼（`ask` + `character=bluefish`）：

> 帮我给 whoever@163.com 起草一封邮件，主题「大肥鱼邮件链路测试」…只建草稿，不要发送。

服务日志（20.8 秒，agent 1 轮、2 次模型调用）：

```
[mail] 待批草稿 draft-8d8e6203750f → whoever@163.com：「大肥鱼邮件链路测试」
[agent] mail_draft({...}) -> √ 草稿已准备好，等你确认
[mail] 草稿 draft-8d8e6203750f 已批准（user），token 有效 300s      ← 用户点了右下角的「发送」
```

审计落盘，正文 hash 也在里面（事后能核对「发出去的是不是批过的那一版」）：

## 67. 附件、过期降权、邮件→日程（2026-11-20 晚，用户要求「加入附件处理和过期降权，同时事件可以和event联动，经我批准后邮件所提事件可以加入event」）

### 67.1 附件：同步只记「有没有」，正文按需抽

Graph 的 `/attachments` 很便宜（一次请求、几百字节），附件正文却可能几十 MB。
所以分两步：同步阶段只存 `has_attachments`；用户真的问到这一封时才拉清单、
再把**能抽的类型**下载下来抽文本（`attachment_chars` 默认 4000 字封顶，
`max_attachment_mb` 默认 8 MB 以上只留清单）。附件名进索引 —— 「那份成绩单 PDF」搜得到。

真机验证（「行程报销校验单及乘机凭证」）：两个 PDF 都抽到了，`行程校验单.pdf` 272 字，
`个人登机凭证.pdf` 只有 19 字（扫描件，没 OCR）—— 这条限制在文档里写清楚了，不假装能读。

### 67.2 过期降权：周三才看到的「周一调课」不该再弹窗

`deadline` 是模型读出来的，规则层看不到；所以降权放在 `classify()` 的最后一步：
日期已经过去 → level 降一档，理由里写明「截止时间已过（11-17）→ 降一档」。

真机效果（同一封邮件、重新分级）：

```
调整思政课授课时间的通知
  level=medium score=85 deadline='2026-11-17' expired=True
  reasons: ['命中「务必」', '发件人标了高重要性', '被你加了旗标', '截止时间已过（11-17）→ 降一档']
```

### 67.3 邮件 → 日程：走的是和发信同一条思路

`mail_to_event(message_id)` 只生成一条 `proposals` 记录（`pending`），然后复用**同一张**审批卡
（按钮换成「加入 / 忽略」，第一行换成「时间」）。点「加入」才调流水线注入的 `add_event`：
它把提议交给 `event_text.parse_datetime` → `EventStore.append`（跨进程锁 + 原子写）。
邮件子系统仍然不认识事件层（边界自测守着），这根线搭在 `pipeline._add_event_from_mail`。

实测两次，**第一次就抓到一个真问题**：

1. 第一次让大肥鱼「把 Assignment 3 那封邮件里的事加进日程」，它**直接调了 `add_event`**，
   绕过了卡片 —— 因为 `add_event` 是所有角色都有的基础工具。修法是把规则写进
   `HARNESS_TOOL_HINT` 和邮件服务器的 INSTRUCTIONS：「从邮件读到的事只能用 `mail_to_event`，
   不要直接 `add_event`，那等于替用户做决定」。
2. 改完再试（期末考试时间表那封），它老实调了 `mail_to_event`，卡片弹出来，用户点了「忽略」——
   状态 `skipped`、`events.json` 里什么都没写。闸门是有效的。

### 67.4 顺手修的两个时间 bug

- **ISO 时间被当成「今天」**：`parse_datetime("2026-11-24 23:59")` 返回的是**今天** 23:59
  （中文解析器只认出了时刻，日期落回 today）。模型给的截止时间多半是这种机器写法，
  不修会把「24 号的截止」记成今天。现在 `nlp_time` 先认 `YYYY-MM-DD[ T]HH:MM`。
- **正文一取就丢了 preview**：`propose()` 拿到正文后只搜正文，而「12月14日截止」这种关键句
  有时只在 `preview` 里（正文被去引用了）。现在正文 + 预览一起搜。
