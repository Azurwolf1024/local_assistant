## 36. 四级记忆：会自己整理、会忘、也认得出「上周三我们聊过什么」（2026-09-26 用户提需求）

用户原话（拆成 6 条需求）：四级记忆架构；**自清洁**（不是一堆死文件）；重要事件总结后
**结构化入库**；**信息检索 + 时间检索**（「过去【时间】里我们关于【事情】的讨论」）；
**深层记忆**（自己的名字这类）；**可接外部/本地知识库**（世界观设定）；
**角色记忆隔离**，但**日程读写权共享**。

### 36.1 四层怎么对应人脑

| 层 | 类比 | 落在哪 | 会不会忘 |
|---|---|---|---|
| L1 原始对话 | 刚发生的事 | `sessions/session-*.jsonl`（本来就有的原始日志） | **会**：滑动窗口，30 天 / 最多 10 个文件（已提取的记录在案就能删） |
| L2 情节 | 记得「那件事」 | `data/memory/<角色>/episodes.jsonl` | **会**：显著性按 60 天半衰期衰减，被回忆到就加回来 |
| L3 事实 | 常识 / 人设 | `data/memory/<角色>/facts.json` | 一般会；**`pinned` 的身份事实永不衰减**（名字、称呼、底线） |
| L4 知识 | 背景设定 | `data/knowledge/*.md` + `config.toml` 的 `world` | 不会（你放什么它读什么） |

`data/memory/<角色>/` **按角色分家**：白泽和凯尔希的经历、事实、知识互不可见。
唯一共享的是 **日程**：记忆只**读** `data/events.json`（`SharedSchedule`），
**写**永远只走技能那一条路 —— 两条写路径必然打架（会互相覆盖），所以宁可一开始就只留一条。

### 36.2 自清洁的五条规则（全是可测的纯函数，`memory/levels.py`）

1. **合并**：两条情节时间相近（≤ 36 h）、关键词覆盖 ≥ 0.3、且共享 ≥ 2 个实质主题 → 并成一条
   （「讨论项目 A」聊了三次不该占三条）。
2. **衰减**：显著性 `eff = 原始^(保留期/半衰期)`，半衰期 60 天；**每次被检索命中就加回一点**
   （回忆奖励）—— 这就是「有生命力」的那部分：常被想起来的活得久。
3. **压缩**：超过 45 天的两条情节若高度重合 → 压成一条（用**原始**显著性比较，不用衰减后的，
   否则两条都快死的时候比较没意义）。
4. **提升**：同一主题在 **≥ 3 个不同日子** 出现过 → 从情节提升为事实（「他每周三有课」）。
5. **裁剪**：情节超 800 条 / 事实超 200 条时，按有效显著性砍尾；原始对话按滑窗删文件。

### 36.3 检索：时间 + 信息

`parse_when()` 认「
昨天 / 今天 / 前天 / 上周 / 上周三 / 最近 7 天 / 上个月 / 去年 / 2026-09-20」；
**认不出来就返回 `None`（不猜）** —— 猜错时间比不答更坏。打分是
`0.5×主题重合 + 0.5×显著性` 再乘上回忆 / 新鲜 / 置信 / 置顶的权重，与时间窗取交。

实际用起来：助手每轮把「最相关的几条记忆」拼成一小段 system 提示（**放在工具提示之前**，
工具提示必须紧贴用户那句话，之前实测过）；也可以手动查：

```powershell
python main.py memory                              # 四层各有多少东西
python main.py memory --recall "导师" --when 上周   # 时间+信息检索
python main.py memory --remember "记住：周五三点见导师"
python main.py memory --knowledge "白泽"           # 只搜知识库
```

### 36.4 开发中被自己抓到的 8 个 bug（这才是本条最值钱的部分）

| # | 现象 | 错在哪 |
|---|---|---|
| 1 | 情节永远不合并 | 关键词按**字典序**取，两条永远取不到同一批 → 改成标题优先 + 传入 `prefer` |
| 2 | 合并条件形同虚设 | 单个汉字也算「共享主题」，随便两条都满足 → 加关键词覆盖率 + 非通用词守卫 |
| 3 | 短知识文件被默默丢掉 | 切段后短于阈值就丢 → 改成永不丢内容的兑底 |
| 4 | 压缩时把活着的和快死的等量齐观 | 比较用了**衰减后**的显著性 → 改用原始值 |
| 5 | 一个主题生成 6 条事实 | 按每个关键词各生成一条 → 改为一组一条（按首关键词分组） |
| 6 | ★滑动窗口从来没生效过★ | `keep_session_files = 200` 把所有文件都保护了起来 → 改成 10 |
| 7 | 时间解析切片错位 | `parse_ts` 的切片长度算错，日期差一天 |
| 8 | ★自测把空文件写进了真实记忆库★ | 测试没关记忆 → 从结构上修：记忆目录默认跟 `data_dir` 走（测试指到临时目录就自动隔离）+ 空内容不落盘 |

另有两个**编辑器层面**的坑（不是逻辑 bug 但差点送出去）：多段替换时误删了
`_write_session` 的函数体（从早先的读取恢复）；另一个多段替换默默吃掉了一句
`from .tts import … create_tts` —— 这种只有真跑才会报 ImportError（静态检查一声不响），
所以改完 `pipeline.py` 必须实际 `import` 一次。

### 36.5 验收

- `scripts/tests/test_memory.py`：11 节 **90 条断言全过**（EXIT=0），已加入 `sessions/run_tests.cmd`；
- 全套 **30 个脚本 ALLDONE**，且跑完后 `data/memory/` **不存在**（测试完全隔离）；
- 命令行实测：`--remember` 写入 → `--recall "导师"` 命中（score 1.62）；
- 默认角色已修正：命令行与助手都落到索引里的默认角色（白泽），不再分家。

### 36.6 还没做（诚实清单）

- **MCP 记忆工具**：现在检索是「每轮自动拼进提示」，模型不能**自己决定**去查。
  加 `recall` / `remember` 两个工具后就能「等等，我查一下以前聊过什么」。
- 情节总结现在优先用**规则**（触发词 + 句型）兜底，LLM 摘要可用但在小模型上不稳定（失败就退回规则）。
- B（切短 69 条）还没训完，训完按 §35 同一口径验收。

## 38. 记忆 MCP 工具 + 角色级知识库：让模型自己去查、让每个 IP 看自己的世界观（2026-09-26 深夜，用户提需求）

用户原话：做 MCP 记忆工具，同时确认不同角色应该可以调用不同外界知识库，也可以调用相同知识库；
比如不同 IP 的角色应该调用不同 IP 的世界观。

### 38.1 知识库分层：共享 / 专属 / 全隔离

原来 `MemoryHub` 只建**一份**全局知识库，所有角色共用 —— 「不同 IP 各看各的世界观」做不到。
现在分三层，**摆法决定谁能看到**：

| 放哪里 | 谁能检索到 |
|---|---|
| `data/knowledge/*.md`（**顶层文件**） | **所有角色**（共享那半边） |
| `data/knowledge/<角色id>/…`（子目录） | **只有那个角色**（专属那半边） |
| 人格文件的 `knowledge` / `world` | 同上，路径可以指到仓库外 |
| 人格文件 `knowledge_shared = false` | 连共享那份都不看（全隔离） |

★关键实现只有一行★：共享库建的时候给 `LocalFilesProvider(skip_subdirs=True)` ——
**不收子目录**。否则 `rglob` 会把所有人的专属世界观一起卷进共享库，
而这件事**不会报错**：凯尔希只是会开始拿白泽的设定回答问题。所以自测里专门钉了
「共享库看不到任何角色子目录」这一条。

分工上也刻意保持干净：`memory` 不认识 `Character`，只收一个「给说明书」的回调
（`persona.knowledge_spec_for`）—— 跟 `schedule` 用协议是同一个思路。
好处是命令行、stdio 独立进程、pipeline 三条路能共用同一份逻辑：
stdio 那边自己读一次角色索引就行（`mcp/servers/memory.py` 里的 `_character_knowledge_for`）。

### 38.2 记忆 MCP 工具：从「被动塞提示词」到「自己去翻」

原来记忆只在每轮把摘要拼进提示词（用户问「上个月那个」时，靠的是摘要恰好带上了）。
现在有了 `recall` / `remember` 两个工具，模型可以自己决定去查、去记。

| 工具 | 干什么 | 默认露出 |
|---|---|---|
| `recall` | 内容 + 时间检索（`when` 直接传「上周三」这种中文） | ✔ |
| `remember` | 记一条（和用户说「记住…」等价） | ✔ |
| `memory_stats` | 四层各有多少 | ✗（只给命令行/外部 agent） |

★只露 2 个是有意的★：工具一多本地小模型就选不准（实测 8 个是甜点，现在 8+2=10）。
隔离靠的是「工具默认操作**当前角色**」：角色 id 在 inproc 下从宿主拿回调（`lambda: self.character.id`），
在 stdio 下读环境变量 `VOICE_LOOP_CHARACTER`，都拿不到就退回角色索引里的默认角色。

另一个必须处理的坑：MCP 的 inproc 服务器如果**另建一个 hub**，读写的是同一批文件、
但两边各持一份缓存 —— 模型刚 `remember` 的东西，这一轮的提示词里就看不到。
所以 `deps` 里传的是**回调**（`lambda: self.memory_hub`），拿到的是同一个实例。

### 38.3 验收

- 新增 `scripts/tests/test_memory_mcp.py`（7 节，无需模型）：共享库不被污染、专属目录隔离、
  人格字段解析、显式路径 + 内联世界观、检索层隔离、三个工具的写入/时间检索/角色隔离、
  以及「独立进程没注入 hub 也要能用」；已并入 `sessions/run_tests.cmd`。
- `test_mcp.py` 的期望从「8 个工具」改为「10 个」，并断言两个记忆工具确实露出
  （带 `mcp__memory__` 前缀）→ 实测 EXIT=0，说明从 pipeline 到宿主到服务器整条路是通的。
- `test_memory.py` / `test_persona.py` EXIT=0（新增字段没破坏老行为）。
- 命令行能看出分层：`main.py memory --who baize` → `knowledge: {'local': 6, 'local:baize': 0}`。

★写自测时我又踩了一个自己的坑★：`check(name, 条件, 说明)` —— 那个三参形式比的是**相等**，
第三参是期望值，于是 15 条断言集体假失败。现在专门加了个 `check_text()` 并把教训写在注释里。

## 39. 白泽的跨角色查询权限 + ★检索的一个真 bug★（2026-09-26 深夜，用户提需求）

用户原话：给白泽开一个能查全部内容的权限，同时查完要说明是从哪个角色的记忆查到的。

### 39.1 权限怎么写

人格文件新增 `"memory_all": true`（默认 `false`）。只有默认助手白泽开着。

- **靠回调拿权限，不靠猜**：`pipeline` 把 `can_read_all=lambda: bool(self.character.memory_all)`
  交给 MCP 服务器；stdio 独立进程则自己读角色索引（`can_read_all_memory`）。
- ★找不到这个角色时**不给**权限★：`registry.get(char_id) or registry.default()` 那种「找不到就
  退回默认角色」的写法在这里是致命的 —— 默认角色恰好开着这个权限，一退回就是**不小心把权限发出去**。
- 命令行 `--all` **不要**权限：那是机主本人在终端上查；权限拦的是**角色**。

### 39.2 来源必须标清楚（这是需求的一半）

`MemoryHub.recall_everywhere()` 返回 `[(角色 id, Hit), ...]`：★每条都带着「它属于谁」★，
混在一起不标来源等于把「这是谁说的」丢掉，比查不到还糟。工具输出与命令行都长这样：

```
★跨角色（以 白泽 的身份查）★查了 3 个角色，命中 4 条。回答时★必须说清楚每一条是谁记的★：
- [凯尔希] [那件事] 2026-09-26 23:43 记住：博士下周要交体检报告
- [白泽] [资料] 白泽的世界：白泽是瑞兽……
```

角色 id 会换成**名字**（白泽 / 凯尔希）：宿主传 `character_label` 回调，独立进程自己查索引。
每轮自动注入的那份摘要**不跨角色**（只带当前角色），跨角色只发生在明着问的时候。

### 39.3 ★顺手撞出来的真 bug★：无关事件能靠「新鲜 + 重要」混进结果

写跨角色的断言时，我让白泽去查「体检报告」（那是凯尔希记的），结果白泽那条
**到导师见面**的事也被翻出来了，还拿到了 **0.96 分**。

原因：打分是**加性**的 ——

```
total = 1.6×主题 + 1.0×重要度 + 0.4×回忆次数 + 0.3×新鲜度
topic = 0 时：0 + 0.75（重要度）+ 0.3（新鲜度）≈ 1.05 × 可信度 → 0.96，远高于 0.12 的门槛
```

也就是说：**只要给个新鲜的、重要的事件，任何查询都能把它翻出来**。提示词里那份「相关记忆」
和工具的检索结果都会带上这种噪声，而这件事**不报错**（只是看起来“它瞎想起”。）。

修法（`Memory.recall` 里两道门）：

1. **给了时间窗**：时间窗内的都算候选（用户可能只记得时间，没给内容词）；
2. **给了内容词**：`topic <= 0` 的**直接淘汰**（事件、事实、知识片段三条路都加）。

这两道门加完，`test_memory.py` 的 90 条断言仍然全过（说明没误伤正常检索），
新自测里则多了三条：「无关查询一无所获」「同角色自己的话题照常查得到」「只给时间仍然能查」。

### 39.4 验收

- `scripts/tests/test_memory_mcp.py` 扩到 8 节 **EXIT=0**（新增：跨角色标注来源、白泽用 `who=*` 能查、
  凯尔希用 `who=*` 被拒、中文写法「全部角色」也认、上述三条门槛断言）。
- `test_memory.py` / `test_persona.py` / `test_mcp.py` 全部 EXIT=0。
- ★同一类错误我在这份自测里犯了两次★：`check(name, 条件, 期望)` 写成了 `check(name, 条件, 说明)`，
  第三参是**期望值**而非说明，于是断言假失败 —— 已经全文 grep 过一遍改成真正的相等比较。

## 40. 世界观组：同一个 IP 的角色共享一套设定（2026-09-26 深夜，用户提需求）

用户原话：考虑不同角色可以共享世界观，比如同为明日方舟的凯尔希和阿米娅就可以共享明日方舟世界观。

### 40.1 问题：原来只有「所有人共享」和「一个人独占」两种

上一版知识库只有两层：顶层文件（**所有角色**）和 `<角色id>/` 子目录（**一个角色**）。
「凯尔希和阿米娅共享明日方舟、但不给白泽」这件事**两头都不占**：
放顶层 → 白泽也会满口源石；放进两人各自的目录 → 同一份设定要拷两份，改一处得记着改两处。

### 40.2 加一层：世界观组

```
 data/knowledge/
     _README.md                    ← 下划线开头 = 结构/说明，不当知识
     通用说明.md                    ← 所有角色
     baize/世界观.md                ← 只有白泽
     kaltsit/补注.md                ← 只有凯尔希（叠在世界观上面）
     _worlds/
         明日方舟/泰拉.md           ← ★挂了「明日方舟」的角色共享★
```

人格文件里一行就挂上：`"worlds": ["明日方舟"]`（可挂多个）。
于是凯尔希和阿米娅共享同一份文件，**想改设定只改一处**；白泽没挂，拿不到。
一个角色的知识库现在是四层叠加（共享 → 世界观组 → 专属 → 内联 world），
`stats()` 里一眼分得清：`{'local': 6, 'local:world:明日方舟': 4, 'local:kaltsit': 2}`。

两个刻意的决定：

1. **`knowledge_shared = false` 只关掉「共享那层」**，世界观组照用 —— 那是它自己挂的，
   属于「这个角色本来就活在这个设定里」（不然凯尔希会说「我不是明日方舟的」）。
2. **下划线开头的一律不当知识**（任何一层）★：`_worlds/` 与 `_README.md` 是**结构**不是正文。
   之前 `data/knowledge/README.md` 被当成知识切出 6 段（模型能把使用说明念出来）。
   ★判断只看**相对知识库根**的路径★ —— 直接看 `Path.parts` 的话，`D:\_work\…` 这种带下划线的
   **上级目录**会把整个知识库静默屏蔽（而且完全不报错，排查起来极费劲）。

### 40.3 验收

- `test_memory_mcp.py` 加到 9 节 **EXIT=0**：两人都拿到世界观里的词、白泽拿不到、
  两人看到的是**同一个来源文件**、stats 分层正确、可以挂多个世界观、下划线文件/目录不当知识。
- `test_memory.py`（90 断言）/ `test_persona.py` EXIT=0。
- 测试里撞到一条：改完人格文件要**先热加载**（`registry.maybe_reload()`）——
  生产里是 pipeline 每轮做这件事；hub 每次取知识库都会重读「说明书」，所以热加载后下一句就生效。

## 41. 白泽默认全知，但★不代入★（2026-09-26 深夜，用户提需求）

用户原话：白泽默认应该拥有所有知识库权限，除非特意关闭，只是注意不要代入，让它以旁观的视角看。

### 41.1 权限：`knowledge_all`（默认跟随 `memory_all`）

上一节的 `memory_all` 只管「跨角色**查记忆**」（而且得显式 `who="*"`）。用户要的是它**默认**
就什么都知道 —— 于是加了知识库那一半：

```json
{ "memory_all": true, "knowledge_all": true }
```

- **`knowledge_all`**：这个角色的知识库里**额外并入**所有 `_worlds/<世界观>/`
  和别的角色的专属目录 + 他们内联的 `world`。于是白泽能聊明日方舟、也能聊别人设定。
- **不写 `knowledge_all` 就跟随 `memory_all`** —— 这正是「默认拥有、除非特意关闭」的写法：
  默认行为只有一个开关要管；想只要一半（能跨角色查记忆、但不看别人世界观）就显式写 false。
- 别人的**记忆**（L2/L3）仍然不自动进提示词，只能通过 `recall` 跨角色查 —— 那是持久的个人经历，
  静默混进每一轮的上下文里既浪费又容易张冠李戴（这条边界是刻意的）。

### 41.2 ★不代入：这是需求里最难的一半★

看得到 ≠ 该说。小模型拿到「源石是世界的基础设定」会直接说「我来自泰拉」——
**而且不会报错**，只是角色逐渐变得不像它自己。所以做了三件事：

1. **每个知识片段带 `owner`**（`Chunk.owner`）：共享/世界观/专属/别人的都能标出「这是谁的」。
   检索输出里长这样：`[资料·凯尔希 的专属资料] …`、`[资料·明日方舟（世界观）] …`。
   注意 `name`（给日志/`stats()` 看，如 `local:kaltsit`）和 `owner`（给**模型**看，如「凯尔希 的专属资料」）
   是两个东西：前者要稳定好过滤，后者要像人话。
2. **系统提示里加一段硬要求**（只在有权限的角色上出现）：
   「你读过很多设定，其中一部分是**别人的**……提到它们时用旁观的说法（「据我所知」「在……的设定里」），
   ★不要说成自己的身份、来历或经历★；除非对方明确问到，不要主动把别人的设定抡出来。」
3. 自己的身份仍然只有一份：人格文件里那些（`name` / `title` / `background`）。

最妙的一点是这三件事彼此不依赖：即使某天 `owner` 丢了，提示词那段仍然拦着它自称泰拉人。

### 41.3 验收

- `test_memory_mcp.py` 加到 11 节 **EXIT=0**：
  · 白泽（全知）**看得到**凯尔希的世界观与专属资料，且**带归属标注**；
  · 阿米娅/凯尔希（无权限）仍然看不见别人的（隔离没被这次放开弄坏）；
  · `knowledge_all: false` 能单独关掉「看别人的」，而跨角色查记忆的权限**不受影响**；
  · 系统提示里确实有「不要说成自己的身份 / 据我所知」，而且**只有**全知角色有这一段。
- `test_memory.py`（90 断言）/ `test_persona.py` / `test_mcp.py` EXIT=0。
- 命令行实测（真实配置）：`baize → {local, local:baize}`（因为仓库里还没有 `_worlds/` 与别人的目录）、
  `amiya → {local, local:world:明日方舟, local:amiya}`。

### 46.1 能：看图那一轮把图塞进最后一条 user 消息（Ollama 的 `images` 字段）

图片现在只有一条生命周期，而且是**看图自己那条**（跟记忆无关）：

| 位置 | 内容 | 保留多久 |

## 47. 图片进记忆：★按人脑那三层做★（2026-09-30，用户说「按人脑行为做」）

用户就一句「按人脑行为做」，翻译下来是三层，而且它们本来就对得上：

### 47.2 改了什么

- `Vision.prune(protect=...)`：被保护的图不管多旧都不碰。

  `kind="vision"` 的情节（标题「看了屏幕截图」，摘要 = 你让我看什么 + 我当时看到什么，显著性 0.7），

- 「上次那张图」：技能原本就认「刚才那张图」（`_V_SRC_LAST`），但读的是**进程内**的 `Vision.last`
  —— 重启就忘 ✗。现在扩展成也认「上次/之前/那天/昨天 + 图/截图/照片」，

## 60. 记忆上云：把 `data/memory/` 镜像到一个私有仓库（2026-11-19）

### 60.1 为什么单独一个仓库，以及为什么 L1 不上云

`data/memory/` 是隐私（第 31 节那次事故的同类数据），主仓库里一直 .gitignore 挡着；
可记忆又要能跨机器用。所以给它一条自己的通道：一个**你确认过是 Private** 的仓库，
用 git 当同步协议 —— 顺手白得一份版本历史（「忘掉的那条还能捞回来」）。

仓库里与第 15 节的四级记忆一一对应，不多不少：

```
memory/<角色>/episodes.jsonl   L2 情景
memory/<角色>/facts.json       L3 事实（pinned 的身份不衰减）
memory/<角色>/sessions.json    L1 索引（哪些原始对话已归档）
memory/<角色>/knowledge/       L4 这个角色自己的资料（.md/.txt/.json，单文件 ≤ 2 MB）
manifest.json                  上次同步的清单：角色 / 条数 / 设备 / 时间
```

**L1 原始对话（`sessions/session-*.jsonl`）刻意不上云**：按设计它是「滑窗 30 天清掉」的
工作记忆，云端留一份既没用（下次归档会重算），又是整段对话原文（最隐私的那份）。
真要归档是另一件事（导出成压缩包自己存），不该混进「记忆」。

### 60.2 两个方向、两套语义（这是设计的核心）

| 方向 | 语义 | 为什么不能反过来 |
| --- | --- | --- |
| 本地 → 云端 | **镜像**：本地删了，云端也删 | 否则「忘掉一条」会被下一次 pull 又拉回来 —— 记忆就不听你的了 |
| 云端 → 本地 | **合并**：按 episode `id` / fact `key` 取新，本地独有的留着 | 换机器时要把云端的经历带回来，但本地刚记的东西绝不能被抹掉 |

合并细节（都在 `merge_episodes` / `merge_facts` / `merge_sessions` 里，纯函数，好测）：

- episode：`updated_at` 晚的赢（同 id）；两边独有的都留；结果按 `(ts, id)` 排序，diff 稳定。
- fact：`last_seen` 晚的赢；`evidence` 取大、`pinned` 或起来、`confidence` 取大、
  `sources` 并集、`first_seen` 取**更早**那次 —— 一条事实「第一次被知道」的时间不该因为合并而变晚。
- `sessions.json`：按文件名并，`extracted_at` 晚的赢。

删掉的旧值不在云端消失，它们还在 git 历史里（`git log -p` 就能看），
所以「镜像」不会变成「不可恢复」。

### 60.3 三道闸门（都是因为「记忆」这东西删错了回不来）

| 闸门 | 触发 | 为什么需要 |
| --- | --- | --- |
| **公开仓库拒推** | 推之前匿名 GET `api.github.com/repos/<owner>/<repo>`，`private: false` 就拒 | 记忆里全是个人信息。匿名查不到（私有仓库正是 404）时**不拦**，只把地址打出来 —— 网络问题不该挡住同步 |
| **本地空目录拒绝同步** | 本地一个角色目录都没有 | 「镜像」碰上「记忆目录指错了 / 自测临时目录」= 把云端清空。宁可什么都不做并提示先 `--pull` |
| **git 全程不交互** | `GIT_TERMINAL_PROMPT=0` + `GCM_INTERACTIVE=never` | 凭据没缓存时**当场失败**，绝不在退出服务时弹个窗把进程挂住 |

自动同步（`[memory] sync_on_close = true`）只在**真的在跟人聊**的两个入口打开
（`cmd_listen` / `cmd_chat` 的 `build_loop(..., auto_sync=True)`）：
底下的 `run_*` 一次性命令也走 `build_loop`，让它们去推云端既没道理，
又容易把自测的记忆推上去。同步本身排在最末（归档 → 巩固 → 清窗口 → 再推），
推上去的才是整理后的记忆；失败只记一行日志。

### 60.4 顺手修掉的一个「静默失效」

排查「为什么 `[memory] sync_remote` 读不到」时发现的：`load_settings()` 里
`Settings(...)` 的构造**根本没有 `memory=` 那一行** —— 也就是说 `[memory]` 整段配置
从来没有被读过，一直用的是 `MemoryConfig` 的默认值。
之所以一直没人发现：默认值刚好和 `config.toml` 里写的一模一样
（`keep_session_days = 30`、`max_episodes = 800`…），改配置「看起来生效」纯属巧合。
这一版补上那一行，顺手核了一遍所有键的现值与默认值一致（所以行为没有任何变化）。

### 60.5 怎么验的

| 验的东西 | 怎么验的 | 结果 |
| --- | --- | --- |
| 结构 / 哪些文件不该上云 | `scripts/tests/test_memory_sync.py` 第 [1] 节：`*.lock`、`*.tmp`、非文本知识库都不进仓库 | 全过 |
| 镜像语义 | 第 [2] 节：本地删一条 → 云端跟着删，且 `git log -p` 里还能捞到那条 | 全过 |
| 合并语义 | 第 [3] 节：假「另一台机器」往云端加/改，pull 后「取新、留本地独有、pinned 不丢、首次时间不变」 | 全过 |
| 公开仓库闸门 | 第 [4] 节：把可见性检查打桩成 `public` → 拒推、远端一个提交都没有、本地仍提交（改私有后能补推） | 全过 |
| 防手滑 | 第 [5b] 节：本地空目录 → 拒绝同步且云端一条没少；云端独有角色不会凭空在本地造 | 全过 |
| 真机 | `python main.py memsync` 推了 6 个角色；再跑一次 → 「云端没有变化，不提交」 | 通过 |
| 回归 | 12 个测试脚本（含 test_memory / test_memory_mcp / test_persona_card / test_offline） | 全 EXIT=0 |

## 62. 记忆再进一步：日上下文连续 + 每晚「做梦」压缩（2026-11-20）

### 62.1 为什么要动 L1

到 §60 为止，L1（原始对话）是「**一次进程一个文件**」：早上喊一次、晚上喊一次就是两个
互不知情的 `session-*.jsonl`，而模型每轮只看得到 700 字摘要 + 20 条事件/事实。
于是三个问题一起出现：

| 现象 | 根因 |
| --- | --- |
| 「我刚才说啥」答不上来 | 上下文按**进程**切，不按**人**连着 |
| 长聊之后越答越飘 | 上下文没压缩，全靠检索挑几条，聊得越久越靠运气 |
| 云端 token 花得快 | 每轮都把「今天所有历史」重新拼一遍 → 前缀一直变 → 缓存永远 miss |

参考成熟实现的做法：Letta 的 sleep-time compute（把「判断」挪到离线做）、
Zep/Graphiti 的双时间事实（旧值不删、标失效）、Mem0 的 ADD/UPDATE/DELETE/NOOP 四动作、
Generative Agents 的 reflection（定期把经历归纳成更高的认识）。
这四个里我们**只借了「判断离线化 + 旧值留痕 + 动作化 + 归纳」四件事**，
刻意没借的是：向量库（本地不需要）、自动覆盖（本地 4B 判断不可靠）。

### 62.2 L1 改成「不可变段 + 打开中的尾」

```
data/memory/<角色>/context/
  segments/seg-000003.jsonl   已封存：★一个字节都不再改★
  segments/seg-000004.jsonl   打开中：每轮只 append
  digests/2026-11-19.json     做梦产出（summary / open_threads / decisions）
  dreams/2026-11-19.json      这次梦改了什么 + 改之前的前镜像（--undo）
  state.json                  seg / seq / turns / tokens / last_dream_seq / cache
```

两条硬规则：

1. **封存只改段号，不动旧文件**。`seal()` 只把 `state.seg` +1，新内容进新文件。
   这是「白天的提示词前缀不动」的**唯一**实现方式 —— 实测断言在
   `test_memory_dream.py [1]`（封存后再 append，旧文件字节数不变）。
2. **压缩不是删除**。封存的段还在磁盘上，`recall` 照样检索得到；
   只是不再逐字进提示词，用 `digests/` 里那几行代替。

提示词布局（`ContextLog.render`）：

```
事实（L3，一天只变一次） → 往日摘要（做梦追加） → 最近原文（只追加）
```

`_tail()` 按 token 预算**从尾往前整轮取**，绝不把一句话切一半（切一半最容易让模型
接错半句）。本地模型单独一档预算（`local_tail_tokens = 800`）：4B 的窗口紧、注意力弱，
塞 2000 token 原文的结果是「记得更少还更爱跑题」。

### 62.3 做梦：一个离线 agent + 五道校验

`Dreamer.run()` 两种跑法（`rule` / `agent`），**同一个出口**：

```
pending = context.new_turns()        # 上次做梦之后新长出来的
  ├─ agent 版：HarnessAgent(read_turns / query_memory / done, plan_tool=False)
  │            → 模型交 {digest, actions[]}
  ├─ 失败/本地角色 → rule 版：episodes_from_session + 规则摘要
  → 五道校验 → 执行 → write_digest → seal → mark_dreamed → consolidate → 前镜像
```

★`plan_tool=False`★：做梦只要一份结构化提议，给它 `update_plan` 只会让它把步骤写进
计划里然后忘了交提议（第一次联调就是这么失败的）。

五道校验（`_apply_actions`）：

| 校验 | 为什么必须有 |
| --- | --- |
| `pinned` 不许 forget/supersede | 名字、称呼是身份，改了就是「换了个人」 |
| `promote.evidence_seq` 必须是 **user** turn | ★防 poisoned consolidation★：工具/网页返回的内容不是对方说的，不能升成事实 |
| `(key,value)` 已存在 → NOOP | 梦境每天跑，不判重就会一条事实记十遍 |
| `max_actions` 上限 | 一次梦改几十条 = 没法复核 |
| 前镜像是**动手之前**抓的 | 见 62.5 的坑 |

`rule` 版还多一道去重：退出时 `ingest_session` 会从原始对话里抽一遍同样的东西，
两条路都走到就重复记 —— 按「日期 + 标题」判重，先来的算数。

### 62.4 五种触发（一个调度器，条件互相让路）

| 触发 | 默认 | 落到哪 |
| --- | --- | --- |
| ① 模型主动 | `mcp__memory__request_dream` 写 `_dream_requests.jsonl` | 下一轮 `tick()` 读走（★只投请求不直接做★：stdio 下那是另一个进程，直接改记忆会跟主进程抢写） |
| ② 长度阈值 | `at_tokens = 3000` | 只做 **rule**（毫秒级、不花 token） |
| ③ 夜间窗口 | `window = "02:00-05:00"`，`random = true` | 每天在这个窗口里**随机**挑一分钟，落 `_dream_schedule.json`（`done` 标记保证一天一次） |
| ④ 空闲 | `idle_minutes = 20` 且 `idle_min_turns = 8` | 白天也能小睡 |
| ⑤ 手动 | `python main.py dream` | 备用扳机 |

`DreamScheduler.request(reason, delay, who)` 是**预留给「随机时间唤醒」**的接口：
以后要做「她自己挑个时间醒过来整理/找你」，调这个就行，不用再动调度逻辑。

★退出时补一次 rule 版梦★（`_dream_on_close`）：夜里那个窗口你要是 23 点关机、
第二天 9 点再开，就永远碰不到，上下文会一天天只增不减。补的这次**只走规则版**
（不花 token、不做价值判断），真正的「该记什么」还是留给夜里的 agent 梦。

### 62.5 开发中踩的四个坑

1. **前镜像抓晚了**：最初 `_write_record()` 在 `_agent_pass()` **之后**抓
   `episodes/facts` —— 存下来的是「改完的样子」，`--undo` 成了空转。
   修法：`run()` 一开始就抓 `before`，一路传下去；顺带把 `last_seq_before` 也记真值
   （以前写死 0，回滚会把 `last_dream_seq` 归零 → 整段历史重做一遍）。
2. **`Episode` 没有 `note` 字段**：`insight` 动作一直静默失败
   （`__init__() got an unexpected keyword argument 'note'` 被 `_apply_actions` 的
   `except` 吞成一条 `skipped`）。教训：批量动作的 except 要留痕，但也**必须有人看**。
3. **`Turn(index=...)` vs `Turn(turn=...)`**：`extract.Turn` 的字段叫 `turn`，
   规则版一跑就 TypeError —— 这条路径此前**从来没有被真跑过**（`_rule_pass` 是这次新写的）。
4. **同一轮写两遍**：`_write_session` 有好几条路径（正常/打断/兜底），重试时 stats 会被
   写两次；而 uid 里带时间戳（秒级），两次的时间戳不同 → 去重失效。
   修法：`_append_context` 里按 `(turn, user_text, answer)` 再拦一道。

### 62.6 双时间事实（Zep 那一半）

`Fact` 加 `invalid_at` / `superseded_by`；`apply_supersede()` 是唯一实现
（`Memory.supersede_fact` 和 `dream._apply_actions` 都调它，只是**写盘时机不同**：
前者自己写，后者在内存里攒、由 `_apply_actions` 收尾统一写）。

`facts()` 默认只返回没失效的；`facts(include_invalid=True)` 能把旧值翻出来 ——
所以「我以前喝什么」答得上来，「现在喝什么」不会被旧值干扰。
`_upsert_facts` 遇到值变化也改走这条路（以前是**原地覆盖**，旧值只剩 note 里一句「原…」）。
`pinned` 例外：名字/称呼直接改，不留旧值当「历史真相」。

### 62.7 缓存记账（怎么知道真的省了）

`OpenAICompatClient` 的请求体加了 `stream_options: {include_usage: true}`
（★不要这个，DeepSeek 就不回 usage★），流里多一种事件 `{"usage": {...}}`；
`pipeline._record_usage` 认两种字段名（`prompt_cache_hit_tokens` / `prompt_tokens_details.cached_tokens`），
落到 `context/state.json` 的 `cache.<日期>`，控制台概览页显示今天的命中率。

### 62.8 上云（追加 §60 的边界）

`memory/<角色>/context/{segments,digests,state.json}` 也镜像过去：换机器后
「今天聊到哪儿」接得上（段是追加文件，镜像过去字节不变，前缀缓存照样命中）。

★隐私边界因此变了，必须写清楚★：段文件里存的是 **user/assistant 原文**
（摘要只用来压缩提示词，不替代存档），所以「L1 不上云」现在**只对滑窗日志成立**
（`sessions/session-*.jsonl` 仍然不上去）。`context/dreams/` 也不上云 ——
那是 episodes/facts 的全量前镜像，只对本机「反悔」有意义。`.lock` / `.tmp` 一律跳过
（本机跨进程锁，上云只会让另一台机器读出脏数据）。

`--pull` 时：

- **段按 `uid` 合并**（两台机器各自追加过同一段时，整段覆盖会丢行），按 `seq` 排序；
- 摘要按日期取 `dream_at` 新的；
- `state.json` 取 `last_dream_seq` 大的那一份，但★`seg` / `seq` 取大的★
  （降了就会往一个已经写满的旧段里追加）。
